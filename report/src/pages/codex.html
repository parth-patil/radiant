Driving the Codex CLI from an app

The app is meant to use the user's existing ChatGPT subscription through the OpenAI Codex command-line tool, with no separate API key. This page establishes how another program can drive the installed Codex CLI (version 0.167.0 on your Mac), what was verified by running it, what is only documented, and what is still unknown. Structured output, streaming, image generation and SVG generation were all exercised successfully with the existing login, so the integration is feasible; the policy position is the one open risk.

Verified hands-on means the behaviour was observed on your machine. Documented means it comes from OpenAI documentation or from the generated protocol schema of the installed binary, without being exercised. Third-party means a blog, package or community source. Unverified means nothing reliable was found or the case was not tested.

What was tested

Ten real model calls were made on one machine, in two passes, with the user's ChatGPT login (plan type reported by the app server as prolite). The first pass checked documentation, flags, policy and two calls to codex exec. The second pass made eight calls, mostly through codex app-server, to verify streaming, image generation, SVG against a contract, and isolation. Every call used a trivial prompt. Three ways in

There are three practical ways for a program to drive Codex: run codex exec once per request, keep a codex app-server process open and speak JSON-RPC to it, or use one of the official SDKs. The app server is the right choice for Radiant because it is the only route that streams, cancels cleanly and reports rate limits. codex exec is a sound fallback. A fourth route, codex mcp-server, no longer exists.

The OpenAI documentation says the codex mcp-server command and binary "have been removed", and that integrations should move to the app server SDK page. The documentation site now answers requests under developers.openai.com/codex/ with a permanent redirect to learn.chatgpt.com/docs/; both host names serve the same content, and the links on this page use the new one.

Using codex exec

A typical call for one structured result, with every flag observed to work on 0.167.0:

codex exec --json --skip-git-repo-check --ephemeral -s read-only \
  --ignore-user-config --ignore-rules -C . \
  --output-schema mm.schema.json -o last1.json \
  "<prompt>" </dev/null

The flags that matter: --json for JSON Lines events; --output-schema FILE to request a final response that conforms to a JSON Schema Non-interactive docs; -o FILE to write the last message to a file; -s read-only for the sandbox (read-only is also the documented default); --ephemeral to skip saving session files; --skip-git-repo-check to run outside a git repository; -m for the model; -c key=value for configuration overrides; --enable and --disable for feature toggles; -i FILE to attach images; and -C for the working directory. There is no --search flag on exec (the top-level codex command has one) and no --full-auto Verified hands-on.

The real call produced exactly four event lines. The model's whole answer arrived in one item.completed event, so there is nothing to display until the call finishes:

{"type":"thread.started","thread_id":"01a1ea70-..."}
{"type":"turn.started"}
{"type":"item.completed","item":{"id":"item_0","type":"agent_message",
  "text":"{\"title\":\"Coffee\",\"nodes\":[ ...5 nodes... ]}"}}
{"type":"turn.completed","usage":{"input_tokens":18277,"cached_input_tokens":0,
  "cache_write_input_tokens":0,"output_tokens":121,"reasoning_output_tokens":0}}

The file written by -o contained the bare JSON and matched the schema. The documented event types are thread.started, turn.started, turn.completed, turn.failed, item.started, item.completed and error, with item types for agent messages, reasoning, command executions, file changes, MCP tool calls, web searches and plan updates Documented Non-interactive docs.

Risk

With a prompt argument and a stdin that is open or not a terminal, codex exec blocks on the line "Reading additional input from stdin..." and never returns. The first attempt hung until the process was killed Verified hands-on. The fix is to redirect stdin from /dev/null or close it when spawning. Passing - as the prompt makes exec read the prompt from stdin instead.

What exec cannot do: show partial output, so a map cannot grow on the canvas during a call; be cancelled other than by killing the process; or report rate limits. Each call also pays roughly 18,000 input tokens of fixed system and tool prompt (inferred from the one cold call; later calls showed cached counts), and parallel processes each pay that again. A mind-map call through exec is one request and one response.

Using the app server

The app server is documented by OpenAI as the interface for "a deep integration inside your own product", for custom clients that handle authentication, conversation history, approvals and streamed agent events Documented SDK page. All the behaviour below was exercised with a small Python client that logs every JSON-RPC line in both directions with millisecond timestamps. Messages are newline-delimited JSON and the jsonrpc field is not required.

Handshake and starting a thread

Spawn codex app-server --listen stdio://, send initialize with client information, then the initialized notification, then thread/start. Keeping experimentalApi false was sufficient for everything used.

-> {"method":"initialize","id":1,"params":{"clientInfo":{"name":"mm_probe",
     "title":"MM probe","version":"0.0.1"},
     "capabilities":{"experimentalApi":false,"requestAttestation":false}}}
<- {"id":1,"result":{"userAgent":"mm_probe/0.167.0 (Mac OS 26.5.1; arm64) ...",
     "codexHome":"/Users/parth/.codex","platformFamily":"unix","platformOs":"macos"}}
-> {"method":"initialized"}
-> {"method":"thread/start","id":2,"params":{"cwd":"<dir>","approvalPolicy":"never",
     "sandbox":"read-only","model":"gpt-6-luna","ephemeral":true,
     "serviceName":"mm_probe","config":{"mcp_servers.context7.enabled":false}}}
<- {"id":2,"result":{"thread":{"id":"01a1ea79-f573-...",...},"model":...,
     "approvalPolicy":"never","sandbox":{...},"reasoningEffort":...}}

thread/start also accepts baseInstructions, developerInstructions and ephemeral Documented (from the generated schema of the installed binary). The approval policy takes untrusted, on-request, granular or never, and the sandbox takes read-only, workspace-write or danger-full-access.

Starting a turn

-> {"method":"turn/start","id":4,"params":{"threadId":"<tid>",
     "input":[{"type":"text","text":"<prompt>","text_elements":[]}],
     "effort":"low","outputSchema":{ ...optional... }}}
<- {"id":4,"result":{"turn":{"id":"01a1ea79-f818-...","status":"inProgress",
     "items":[],"itemsView":"notLoaded",...}}}

The turn identifier comes from this response and is needed for interruption. turn/start can override model, effort, cwd, approvalPolicy, sandboxPolicy, summary and outputSchema, and an override applies to that turn and later turns. Input items can be text, image, localImage or skill Documented App-server docs.

The notification sequence

For one text turn the client saw, in order Verified hands-on: remoteControl/status/changed; account/updated (auth mode chatgpt, plan type prolite); thread/started; one mcpServer/startupStatus/updated per MCP server (this does not block the turn); thread/status/changed to active; turn/started; item/started and item/completed for the user message; item/started for the agent message (phase final_answer, empty text); many item/agentMessage/delta; item/completed for the agent message with the full text; thread/tokenUsage/updated; account/rateLimits/updated; thread/status/changed to idle; and finally turn/completed.

Deltas arrive in bursts about every 110 to 150 ms, each burst holding three to nine delta messages that share a timestamp, in chunks of one to twelve characters (sub-word tokens). The delay of about three seconds before the first delta is mostly model and network latency, not MCP start-up.

Structured output streams as partial JSON

A recursive schema with $defs, $ref and additionalProperties: false was accepted. The deltas are literal fragments of the final JSON text, for example {", title, ":", Coffee, ",", children, ":[. A streaming JSON parser could create nodes as each object closes, and the final item/completed message carries the whole JSON string Verified hands-on.

JSON Lines is easier to consume

Without a schema, the model was asked for one compact JSON object per line with the fields id, parent and title, parents always before children, no code fence and no other text. It obeyed. Complete lines appeared at 309, 585, 874, 1,163, 1,456, 1,740, 2,019 and 2,309 ms after the first delta, about 3.4 nodes per second, for example:

{"id":"n1","parent":null,"title":"Coffee"}
{"id":"n3","parent":"n2","title":"Ethiopia"}

The client buffers deltas, splits on newlines, parses each complete line and discards a trailing partial line if the turn is interrupted. This is simpler and more robust than incremental JSON parsing. The trade-off is that nothing enforces validity, so each line must be validated locally Verified hands-on. The run was interrupted at 6 s, so the log shows eight lines and not the full 40 nodes the prompt asked for.

Completion, usage and interruption

  • turn/completed carries turn.status (completed or interrupted), durationMs, items and an error field Verified hands-on.
  • thread/tokenUsage/updated reports total and last-turn input, cached input, cache-write input, output and reasoning tokens, plus a model context window of 258,400. It is not sent for an interrupted turn Verified hands-on.
  • Interruption: send {"method":"turn/interrupt","id":5,"params":{"threadId":"...","turnId":"..."}}. The server answers with an empty result, then turn/completed with status interrupted about 2 ms later (duration 6,039 ms in the run) Verified hands-on.
  • After an interrupt the turn's items came back as an empty list (itemsView was notLoaded). The client must therefore keep its own copy of every delta; the server will not hand the partial text back Verified hands-on.
  • With approval policy never no server-initiated approval request ever arrived; the probe script auto-declines any that do Verified hands-on.

Rate-limit calls, model and effort per turn

account/rateLimits/read (parameters {}) returned, on this account, ordinaryUsageAllowed: true and a snapshot with limit id codex, a primary window of 10,080 minutes (one week) at usedPercent: 1, no secondary window, a credits block, plan type prolite, rateLimitReachedType: null and spendControlReached: false. The notification account/rateLimits/updated fires after each turn, sparsely, so the client should merge it into its last full read Verified hands-on. This account shows only a weekly window and no five-hour window. The model and reasoning effort can be set per thread or per turn; low was accepted and gpt-6-luna and gpt-6.1-terra were both used Verified hands-on.

Generated bindings and the experimental label

codex app-server generate-json-schema --out DIR and generate-ts --out DIR both worked offline. The JSON Schema output was 39 files, and the client request type lists 106 methods, among them initialize, thread/start, thread/resume, thread/fork, turn/start, turn/steer, turn/interrupt, model/list, account/read, account/rateLimits/read, account/usage/read, config/read and mcpServerStatus/list Verified hands-on. Because the CLI labels the app server [experimental], the protocol may change between versions. Pin the version found by codex --version and generate types from that binary. Many methods are gated behind experimentalApi, and plugin methods are described as not for production clients yet Documented App-server docs. Open-source clients exist as prior art (a Rust crate and a Codex harness plugin) Third-party vtcode client OpenClaw. No Swift, Elixir or Zig client was found.

Isolation from the user's own setup

A child process of the app inherits the user's Codex home and login, which is what makes the subscription work. It also inherits the user's configuration, including their own MCP servers, and the account's connected apps. A generation job should run with none of these. Isolation can be made good, but not complete, so the sandbox and approval policy remain the real guard.

What leaked

In pass 1, even with --ignore-user-config --ignore-rules, the model's tool list included account-level connector tools (mcp__codex_apps__github, gmail, google_drive, chatgpt_space and others), sub-agent tools (collaboration.*), image generation, web, view-image, patch and exec tools Verified hands-on. On the app server, which has no --ignore-user-config, the user's own MCP servers started alongside the built-in ones.

What worked for exec

codex exec --json --skip-git-repo-check --ephemeral -s read-only \
  --ignore-user-config --ignore-rules -C . \
  -m gpt-6-luna -c model_reasoning_effort=low \
  --disable apps --disable plugins -c web_search=disabled \
  "<prompt>" </dev/null

The minimal recommended set is --disable apps --disable plugins plus -c web_search=disabled; --ignore-user-config already keeps the user's own MCP servers out. The most restrictive run (call 3 above, which additionally disabled multi-agent, shell, unified-exec, browser, computer-use, goals, memories, image-generation and view-image features) removed every connector, web, image and patch tool. What remained was functions.exec, functions.wait, clock.sleep and five collaboration.* sub-agent tools. Disabling code_mode_host is counter-productive: it adds an error item saying code mode is unavailable and functions.exec stays anyway Verified hands-on. The configuration key for web search is web_search with values disabled, cached, indexed and live.

What worked for the app server

The spawn command used throughout pass 2 was codex app-server --listen stdio:// -c web_search=disabled --disable apps --disable plugins --disable multi_agent --disable multi_agent_v2 --disable browser_use --disable browser_use_external --disable computer_use --disable in_app_browser --disable goals --disable memories --disable hooks, with --disable image_generation --disable view_image added for read-only text jobs. A separate probe that starts the server and a thread, and waits five seconds for MCP start-up notifications without any model call, measured which variants actually remove servers:

What could not be removed

No feature flag removed the collaboration.* sub-agent tools or the functions.exec tool, and --disable shell_tool with --disable unified_exec did not take away the shell-like tool Verified hands-on. Whether collaboration.spawn_agent can actually spawn an agent in a read-only thread with no connectors was not exercised Unverified.

Decision

Treat the read-only sandbox and approval policy never as the real guard, and the feature and MCP disables as a way to keep jobs fast, private and predictable. No model run attempted to use connectors, files outside its scratch directory, or the web, in any of the ten calls.

Image and SVG generation

Image generation

Image generation works with the ChatGPT login and no API key. The model calls its built-in image tool when the prompt asks for an image; no flag is needed. The tests used --sandbox workspace-write and the image feature left enabled Verified hands-on.

  • Call 1, red apple. The prompt asked for a flat-vector red apple on a plain white background, square, with the reply being only the file path. An imageGeneration item started at +5.9 s and completed at +18.1 s, so generation took 12.1 s and the turn 20.5 s. Tokens were 15,956 in and 101 out; image cost is not included in those counts.
  • The result is returned inline. The completed item carried status, revisedPrompt (the model's own rewrite of the request), transparentBackground (false here), failure, generationId, savedPath and result, a base64 PNG of 1,417,676 characters. The schema also allows a fileId in place of result, but inline data was what came back. Decoded, the file is a PNG of 1254 by 1254 pixels, 8-bit RGB, no alpha channel, 1,063,257 bytes. The base64 begins with C2PA provenance metadata.
  • Codex also saves a copy. It writes the image to ~/.codex/generated_images/<threadId>/ itself, outside the job directory, because the sandbox restricts the model's tools and not this host-side save. The app should read result or savedPath, copy the image into its own store, and may delete the Codex copy.
  • Call 2, transparent pear with a reference image. A localImage item holding the apple was appended to the turn input, and the prompt asked for the same style, a green pear and a transparent background. The item came back with transparentBackground: true. The PNG is 1254 by 1254 RGBA, 516,842 bytes, with a corner pixel alpha of about 0.004 and 28.7 percent of pixels opaque (so about 71 percent transparent). Generation took 29.2 s (item started at +7.8 s) and the whole turn 38.5 s. Tokens were 17,966 in and 216 out, then 20,370 in (17,920 cached) and 64 out. The model rewrote the prompt to ask for a "real alpha channel" and to match the reference's style.
Evidence

Third-party writing says the gpt-image-2 model rejects a transparent background and recommends a flat-colour chroma-key workaround Third-party Vaughan 2026. The hands-on result contradicts that for the built-in tool: a genuine alpha channel was returned. This is one sample, so the app should still check the alpha channel of each result and keep a local background-removal fallback.

What cannot be controlled: the model, not the client, chooses the tool arguments. Only revisedPrompt and transparentBackground are visible on the item, and size came out as 1254 by 1254 for a "square" request. No size, quality or seed control was found Verified hands-on. A seed is also not documented for the built-in tool Unverified.

What was not tested: asking for "the same style as the previous image" inside one thread without attaching it; whether the pear visually matches the apple (the reference image visibly changed the revised prompt, but the match was not judged); how many image turns one plan allows; and the exact event shape of an image in exec --json. The documentation says image generation uses included limits "about 3-5x faster" than similar non-image turns, depending on quality and size, that it is not available on the Free plan, and that it draws credits once limits are exhausted Documented Pricing. That rate could not be checked because the usage meter did not move.

SVG generation

The test asked gpt-6.1-terra at low effort, through the app server in a read-only sandbox with image tools disabled, for an SVG that meets a node-group contract for a five-node map. It took 28.7 s in total, with the first delta at 2.8 s and 1,438 deltas, so SVG text streams and could be previewed progressively. Tokens were 13,923 in and 1,443 out, with no reasoning tokens Verified hands-on.

A checker script (XML parsing with approximate bounding boxes from path coordinates, ignoring transforms) found the following. All checks below passed.

  • Well-formed XML of 3,558 bytes with viewBox="0 0 800 600": one svg, six g (five node groups and a connectors group), 17 path, five rect, three ellipse, one circle.
  • No script, text, image or foreignObject elements, no external references, exactly the five palette colours and nothing else, and 17 paths against a limit of 60.
  • Groups node-n1 to node-n5 all present, each with data-anchor-in and data-anchor-out in valid x,y form, anchors inside the target box and each group's bounding box inside its target box. For example, n1 had in 315,255, out 485,255 and bounding box [315,255,485,345] inside [300,240,500,360].
  • A render with the macOS WebKit renderer (qlmanage) showed five rounded cards with coherent icons (a cup with steam, a globe, a dripper, two beans, a flame) joined by curved connectors.
Not verified

Weaknesses found. For four of the five nodes (n2 to n5) the in-anchor and out-anchor were the same point, and the root's anchors sat at the edge midpoints rather than meaning "towards the parent" and "towards the children", so the prompt must define anchor semantics. The model drew its own connectors in a connectors group because the prompt allowed it; the app will want to draw connectors itself and must forbid them. Two rotate() transforms inside n4 are outside the checker's bounding-box arithmetic, although they stayed inside the box visually. This is a single sample from one model. A weaker model (gpt-6-luna) and larger subtrees were not tried.

Do not validate generated SVG with ImageMagick's built-in SVG renderer. It drops the connector group and misplaces ellipses that use rotate(a cx cy), so it draws a correct file wrongly. Use a browser engine, which is also what decision D-12 relies on. The design of image and SVG subtrees is on the picture and SVG subtrees page.

Models, plans, limits and errors

Models and effort

codex debug models printed the local model catalogue, which may reflect this account Verified hands-on. It listed gpt-6.1-sol (default effort low), gpt-6-astra (medium), gpt-6.1-terra (low), gpt-6-sol, gpt-6-luna (medium), gpt-5.6-sol, gpt-5.6-terra and gpt-5.6-luna. Effort levels are low, medium, high, xhigh and max, plus ultra for every model except Luna. All accept text and image input and each has a fast speed tier. Two further entries, gpt-reserve and codex-auto-review, are hidden. OpenAI describes Astra as the most capable, 6.1 Sol as near Astra at lower cost, 6.1 Terra as fast and good at writing and visual understanding, and Luna as the most efficient for high-volume focused tasks, with Free and Go plans getting Luna Documented Models. The documentation does not mention a model_reasoning_effort key; it was accepted when passed, but its effect was not measured separately.

The tests used gpt-6-luna at low effort for tool lists, outlines, schema-bound trees, JSON Lines and both images, and gpt-6.1-terra at low effort for the SVG. Whether the image tool depends on the text model chosen was not tested. A blogger's informal pelican-on-a-bicycle SVG tests report that GPT-6.1 Terra at maximum effort produced "a good pelican and a good bicycle" Third-party Willison; no SVG benchmark numbers were found.

Plans and limits

Codex is included with ChatGPT Free, Go, Plus, Pro, Business, Enterprise and Edu plans, and with an API key at pay-as-you-go prices. The published monthly prices are Free $0, Go $8, Plus $20, Pro from $100 (tiers of $100, $200 and $500) and Business $20 per user on annual billing or $25 monthly Documented Pricing. The same page shows five-hour message limits only for Plus and standard Business (for example, GPT-6.1 Sol 15 to 160, GPT-6 Luna 350 to 3,000 and GPT-6 Astra 5 to 45 local messages per five hours), says "Pro plans currently have no five-hour limit", says weekly limits "may also apply", offers credits for Plus and Pro, lists Fast at 2.5 times and Ultrafast at 8 times the included-usage multiplier, and points to /status in the CLI and a usage dashboard.

Not published: the weekly caps per plan as numbers. Third-party blogs disagree on whether a five-hour window was removed on 12 July 2026 and later reinstated Third-party eesel Morph. The account tested shows only a weekly window of 10,080 minutes, consistent with the Pro statement. The app should treat limits as opaque and per user, and read them from the app server instead of assuming numbers.

Errors in the protocol

Failures arrive as an error notification (ErrorNotification with a TurnError, a willRetry flag, thread and turn ids) and, or, as turn/completed with status failed and a turn.error. The codexErrorInfo field takes values including usageLimitExceeded, rateLimitExceeded, unauthorized, serverOverloaded, contextWindowExceeded, modelNotFound, badRequest and sandboxError, and objects for HTTP and response-stream connection failures that carry an HTTP status code. Rate-limit snapshots carry rateLimitReachedType (one of rate_limit_reached, workspace_owner_credits_depleted, workspace_member_credits_depleted, workspace_owner_usage_limit_reached, workspace_member_usage_limit_reached) and spendControlReached Documented (generated schema of the installed binary). In exec --json, errors appear as an item.completed event with an item of type error (seen once, for the code-mode warning), and the documentation names turn.failed and error events; a non-zero exit code is expected.

Not verified

No error was triggered live. The exact wire examples for rate-limit exhaustion, expired or revoked login and a failed turn are unknown, and the behaviour when a refresh token is revoked was not tested. Tokens refresh automatically during use Documented Auth docs.

Policy

The policy position is uncertain, and the report states that plainly. No OpenAI text was found that explicitly permits or forbids a personal desktop app spawning the user's own installed codex binary with the user's own login. A search of OpenAI's documentation, and the pages that could be fetched, turned up nothing either way Unverified.

  • What OpenAI says about credentials. The authentication documentation says to treat ~/.codex/auth.json "like a password", and the non-interactive documentation describes ChatGPT authentication in automation as intended for enterprise teams on trusted runners or users who need ChatGPT and Codex rate limits, and says not to use it for public or open-source repositories Documented Auth docs Non-interactive docs. These statements concern sharing or hosting credentials, not a person running Codex on their own machine. Credentials live in ~/.codex/auth.json or the operating system keyring, and the CLI and IDE extension share the cached login.
  • The "Sign in with ChatGPT" programme. OpenAI publishes a recipe for running codex app-server in a third-party app with an OAuth access token "authorized for ChatGPT plan usage", with the client name acting as a stable application identifier Documented SIWC recipe. The documentation navigation lists "Terms and policies" and "Preview limitations" pages that could not be fetched (errors 404 and 403).
  • Programme details come from one secondary source. A WorkOS summary reports a scope named chatgpt.tokens.use.direct, an announcement at DevDay on 29 September 2026 with 16 partners, Plus and Pro plans only, a focus on open-source and locally hosted apps with paid or remote products directed to an interest form, per-app weekly caps, access tokens lasting 3,600 seconds and refresh tokens 30 days, two named HTTP errors, a requirement to send store: false and stream: true, several tools unavailable on the plan-funded HTTP path (including image generation), and a rule that apps may not charge users for the plan usage consumed Third-party WorkOS. This was not checked against OpenAI's own pages. An OpenAI help-centre article on using a ChatGPT plan in other apps exists but returned an error when fetched, and search snippets disagree on whether Go plans qualify Help centre.
  • Community claims. Some community packages say OpenAI sanctions the Codex OAuth flow for Codex tooling and personal use; other sources say there is no general third-party OAuth registration. Reliability is low Third-party yage.ai manifest.build. Several open-source tools (OpenCode, Cline, OpenHands, Pi) call the backend directly with the OAuth token instead of spawning the CLI OpenHands Cline.
Decision

For a personal tool, spawning the user's own first-party binary with the user's own login is the lowest-risk reading, because the app never touches the credentials. Radiant must never read, copy or relay auth.json or keyring contents, and should check login state only with codex login status (which printed "Logged in using ChatGPT"). Sharing or selling the app later is a different question: asking users to install Codex and sign in themselves, then spawning it, is plausibly acceptable but is not explicitly approved in anything that could be read. The officially supported route for a distributed app is the Sign in with ChatGPT programme, whose open-source and local-app case is the documented sweet spot. Confirm the terms with OpenAI before any public distribution; this is listed as an open item on the roadmap.

What this means for Radiant

The recommended integration follows decision D-07 (see the stack decision): one long-lived app-server process as the primary route, one-shot exec as the fallback, everything behind a provider interface. The requirements built on this are on the AI generation page.

Radiant interface and map engineApplies validated node lines as they arrive, owns layout, and shows rate-limit status and job progress.
Provider interface (host core)Normalised events: node line, delta, usage, error, limits. Codex is the first provider; an API key, another vendor's CLI or a local model can follow.
Codex provider, primary: app-serverOne long-lived codex app-server --listen stdio:// child, types generated from the installed version, one thread per job, turn/interrupt to cancel, rate-limit read and notifications surfaced, per-job empty working directory, isolation settings applied.
Codex provider, fallback: execOne-shot codex exec with the isolation flags above, --output-schema, stdin from /dev/null; no streaming, 7 to 9 s per call.
The user's installed Codex CLI and loginNever read or copied by the app. Version checked with codex --version; login checked with codex login status.
  • Map generation should use the line-oriented stream (decision D-08). Eight complete lines were observed at about 290 ms each after a first delta at 2.8 to 3.7 s, so a few dozen nodes plausibly take on the order of ten to fifteen seconds. Schema-checked JSON via outputSchema or exec is the non-streaming fallback.
  • The client must keep its own copy of all deltas, because an interrupted turn returns no items.
  • The image result must be copied from the inline data or savedPath into the app's store (decision D-19 keeps assets local), and the alpha channel of every image checked.
  • The SVG prompt must define anchor semantics, forbid connectors and text, state the element limit, and the result must be validated mechanically, then rendered in a browser engine.
  • Rate limits must be read before large batches. Per-image cost is unknown, so large image batches need a confirmation step.
  • Concurrency should stay low (two to four jobs, inferred from the roughly 18,000-token fixed prompt of each separate call and per-account limits) and every job should record the prompt and model (decision D-19).

Limits of this research

  • Each hands-on result is a single sample on one machine, one account (plan type prolite) and one version (0.167.0). Timings will vary with load and network.
  • No live error was triggered, so the wire shape of rate-limit exhaustion, expired login and failed turns is known only from the generated schema.
  • Per-image cost in plan usage is unknown because the weekly meter stayed at 1 percent. The "3 to 5 times" figure is documented, not measured.
  • The effect of the effort setting was not measured separately, enabling live web search was never run, and whether collaboration.spawn_agent can actually spawn in a locked-down thread was not tested.
  • Only one SVG sample, from one model, was produced; larger subtrees and the cheaper model are untested. The visual match between the two images was not judged.
  • The policy position rests on the absence of a text, plus one secondary source for the programme details; the primary terms pages could not be fetched.
  • The SDKs' streaming behaviour is unconfirmed, no Swift, Elixir or Zig client libraries were found (GitHub was not searched exhaustively), and local image models were not researched.
