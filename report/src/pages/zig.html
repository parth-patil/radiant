Zig, nanoui and the WebView shell

You asked whether the Zig library called Nano UI is a good fit, and whether a lightweight Zig container around a WebView is a good idea. The short answers are no for nanoui as the foundation today, and workable but pointless for the WebView shell. Zig keeps a credible place as the language of a core library behind a native Swift shell. The overall stack decision is made on the stack page; this page gives only the verdicts on the Zig options and the evidence behind them.

nanoui as the foundation

Verdict: not a fit today

Its canvas has no Bezier curves, no retained geometry and no variable-width strokes, and the project is four weeks old with an API that is allowed to break at every minor release.

A Zig shell around a WebView

Verdict: workable, adds little over Tauri

The shell is thin, so Zig's strengths do not matter, and the Zig WebView bindings are far less mature than Tauri's plugins, signing and updater tooling.

A Zig core with a native Swift shell

Verdict: the strongest Zig option

This is how Ghostty is built. Zig holds the document model, layout and geometry, and AppKit supplies text editing, menus and a Metal view with 120 Hz pacing.

Implication for Radiant

The strongest case for nanoui is real: a 0.7 MB binary, input-method editing on macOS, native menus, file dialogs, drag and drop, clipboard, and frame pacing that asks for the display's fastest rate (up to 120 Hz). That is more of the "boring native surface" than any other Zig option offers. The case against is that all of it rests on a four-week-old codebase whose author expects to break it.

The Zig WebView shell

A Zig shell around a system WebView is technically possible by several routes. The shell would be thin, so Zig's performance advantage does not matter, and the canvas bottleneck would be the WebView itself. The notes judge that Zig buys little over Tauri here and that Tauri is far more mature. Documented for the library facts below; the comparison is the researchers' judgement.

Zig is still before version 1.0, with large breaking releases every five to eight months. Your installed version is 0.17.0 Verified hands-on. The notes recommend budgeting real maintenance time for every release.

The wider Zig GUI ecosystem

The notes conclude that no Zig GUI toolkit is production-grade for a rich-text, input-method-capable, accessible, multi-panel desktop app, and that no widely used editor-style GUI app built on a Zig-native toolkit was found. dvui is the most active and mature. Rich text and SVG would have to be assembled from C libraries whichever toolkit is chosen.

How Ghostty does it

Ghostty, a terminal emulator with about 64,000 stars, is the flagship serious Zig application. It deliberately does not use a Zig GUI toolkit. Its core is a Zig library with a C-compatible interface, with a Swift application using AppKit and SwiftUI on macOS and the GTK 4 C interface on Linux. Ghostty about Its author, Mitchell Hashimoto, reports that about 93 percent of the repository is Zig and C business logic and about 4 percent is the macOS Swift interface. He chose native interfaces per platform because a truly native macOS app needs Swift, and Objective-C was impractical. The build packs a static library with libtool and lipo into an XCFramework. He also notes that the pattern works with any language that has a C interface, Rust included, and that the code held up for over a year through macOS updates while Zig kept changing. Third-party Hashimoto

A secondhand summary of a 2025 interview says the Ghostty interface was written five times (GLFW, SwiftUI, AppKit with SwiftUI, GTK and others). The notes advise treating this with care. Terminal Trove

This is the notes' architecture C and the best-evidenced Zig route. Zig would hold the document model, layout, spatial index and geometry tessellation, producing vertex and instance buffers in shared memory. A Swift and AppKit shell would own a Metal view driven by CADisplayLink for ProMotion pacing, and would get real native text editing, input methods, menus and accessibility without rebuilding them. The cost is two languages and the boundary between them, and a new shell for each later platform, as Ghostty needed. Zig-to-WebAssembly for a later web build is demonstrated by nanovg-zig. nanovg-zig

The researchers estimate (not measure) three to five months to a minimum viable version for a developer comfortable in both Swift and Zig, and rate the risk medium. They also say the same architecture with a Rust core is equally valid: Zig's edge is build and C interoperability, Rust's is its ecosystem (lyon, Vello, wgpu). No published example of a Zig core driving a Metal canvas at 120 Hz with thousands of curves was found.

Where Zig could still fit

If you want to use Zig without betting the app on it, three routes follow from the evidence. They are suggestions drawn from the notes, not tested plans.

  • A self-contained core component, later. The layout engine or the tapered-branch tessellator could sit behind a C interface and be called from a Swift or Rust application. Zig's C interoperability and cross-compilation suit this, and churn stays confined to one library with a pinned toolchain.
  • Reuse or study nanoui's SVG rasteriser. src/ui/svg.zig is a self-contained pure-Zig function that renders SVG bytes to premultiplied pixels at a requested size. It could rasterise SVG subtrees into textures at zoom thresholds. The gap against model-generated SVG is real: text, filters, patterns and markers would silently disappear. svg.zig ThorVG through its C interface is the alternative.
  • Revisit nanoui after it stabilises. The notes suggest re-evaluating in three to six months. Signals to watch for: a path API with curves or a retained mesh primitive, mipmapped image textures, a 1.0 release or a slower release cadence with listed breaking changes, a stable Zig toolchain with ZLS working again, and independent apps of some size built on it.
Idea for Radiant

If the app ever has a self-contained geometry core, build it behind a plain C interface first. That keeps Zig, Rust or C++ all possible for the core and keeps the Swift shell unchanged.

Limits of this research

  • Nothing was built or run. The only hands-on fact is the installed Zig version.
  • No benchmark exists for 5,000 tapered curves at 120 Hz in any Zig library. The per-frame figures for nanoui are arithmetic.
  • Files not read in full: text.zig, textfield.zig, context.zig, page.zig, ipc.zig, and the source of nanofly, nanoterm and nanodocs.
  • Not verified: which Windows renderer path nanoui uses, whether the asset scheme can stream dynamic binary data, the behaviour of the GPU hook when drawing directly into the drawable, WebView frame pacing on macOS 26 (see the measurement page), Tauri details, and input-method or multi-window support in sokol, raylib and zgui.
  • The Zig 0.17 release date rests on a secondary source. The Codeberg search for other Nano UI projects could not be read.
  • All effort estimates are the researchers' judgement and no real-world effort data for Zig GUI applications was found.
