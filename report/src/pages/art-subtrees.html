Picture and SVG subtrees

Radiant lets any subtree of a map be shown as a set of generated pictures, one per node, or as one piece of generated SVG artwork, while the branches, labels, collapse and editing stay under the engine's control. Vector, picture and SVG are three representations of one tree, so a subtree can always return to plain nodes. The two building blocks were checked on your Mac with the Codex command-line tool: a transparent PNG with a style reference attached, and an SVG that passed every mechanical check of a node contract, each from a single sample.

Implication for Radiant

This is the one feature that no existing product offers. A search of the market found per-topic stickers in Xmind and one hobby generator that puts a single generated image at the root of a map, and nothing that turns a subtree into generated art while it stays a live, collapsible map Xmind blog Agent.ai generator. The search was limited, so the absence is a finding about this report's search and not a proof. Most of the mechanisms on this page are therefore Proposed design and the first spike should test them before the rest is built.

The engine mechanics underneath (textures, caching, layout algorithms) are on the engine page. The protocol that carries image and SVG requests to Codex is on the Codex page, and whole-map generation is on the AI engine page. The requirements on this page use the prefix FR-ART. They are scheduled for milestones M4 (picture subtrees) and M5 (SVG subtrees) on the roadmap; a Must here means the feature is not delivered without it, and a Should is part of version 1.

One tree, three representations

A representation is the way a subtree is drawn. In the vector representation every node is a text shape that the engine draws. In the picture representation every node is a generated image with a label drawn on top by the engine. In the SVG representation the subtree is drawn as one piece of SVG artwork that the engine has divided into one group per node. The document stores a single tree in every case (decision D-09), and each node keeps its text, notes and identity, so search, outline, export and screen readers work in every mode. Representation is a property of a subtree, not of a node, and each node in the subtree draws itself according to that property.

What stays under engine control

  • Branches. The engine draws every branch, including the one that joins the subtree to its parent, so branch style, width taper and colour stay consistent. Generated art never draws a connector.
  • Labels. The engine draws every label as live text. Image models still make text errors, and a label baked into a bitmap cannot be searched or edited.
  • Selection, drag and hit-testing. Each node has a layout box, and clicks resolve against the box or, for SVG, the node group.
  • Collapse state. The engine owns it and hides or shows nodes, whatever they look like.
  • Layout. A node's box is its representation's box. Switching representation changes the box and triggers an incremental re-layout of that subtree only (engine page).

Nesting rules

These rules are Proposed design because nothing in the notes covers them. A picture subtree or an SVG subtree may sit inside a vector map, and a vector subtree may sit inside an art subtree: the parent's art simply continues as a normal branch into vector nodes. A picture subtree may contain an SVG subtree as a separate island with its own style sheet. An SVG subtree must not contain picture nodes, because one SVG artwork is generated as a whole and a picture inside it would need a separate image reference, which the contract forbids. When a user applies a different representation to a node inside an art subtree, the app splits the subtree at that node and the new subtree gets its own style sheet.

Implication for Radiant

Switching is non-destructive: generated assets stay in the document store keyed by an input hash, so switching a subtree to vector and back reuses them if nothing changed. This lets a user try art on a subtree with no lasting commitment.

FR-ART-01Must

Three representations of one tree

Every subtree must have exactly one active representation, chosen from vector, picture and SVG, and the document tree must remain the only source of truth for node text, structure and identity.

Accept when: Switching a subtree of 20 nodes between all three representations and back leaves node ids, text, notes and order byte-identical in the saved document. Why: Decision D-09; see the vision.

FR-ART-02Must

Text survives in every mode

Every node in a picture or SVG subtree must keep its text in the document, and search, the outline view, text export and screen-reader output must read that text regardless of representation.

Accept when: With a picture subtree active, a search for a keyword inside it finds the node, the outline lists it, and the accessibility tree exposes its text. Why: Accessibility and export depend on text; quality requirements.

FR-ART-03Must

Reversible, non-destructive switching

Switching a subtree to vector must be possible at any time without loss of generated assets, and switching back to picture or SVG must reuse cached assets whose inputs have not changed.

Accept when: Switch picture to vector to picture on a 10-node subtree: no model call is made and the same assets are shown. Why: Users must be able to try art without risk.

FR-ART-04Should

Nesting rules

A picture subtree and an SVG subtree must be allowed inside a vector map, and a subtree must not contain a subtree of a different art representation unless the user has switched it explicitly; a picture subtree may contain an SVG subtree only as a separate island with its own style sheet.

Accept when: Selecting a node whose parent subtree is SVG and choosing picture is refused with a message, or creates a separate island after confirmation. Why: Proposed rule; see the nesting section above.

FR-ART-05Must

Engine-owned elements

In every representation the engine must draw branches, labels and selection, own collapse state, and perform hit-testing; generated art must never carry connectors or text.

Accept when: In picture and SVG subtrees, clicking a node selects it, renaming it changes the live label, and no generated asset contains a connector or text element. Why: Decisions D-10 and D-11.

Why art helps memory

The reason for this feature, in the user's words, is that generated images and SVG make a map "much more beautiful and organic-looking" with "very unique elements", which should make it easier to remember. The evidence supports part of that claim and puts limits on the rest. The full evidence is on the evidence page; the chain below shows what follows for the product.

From memory research to the product stance
ClaimStrengthWhat it means for art subtrees
Pictures help when they carry the meaning of the node (representational and mnemonic pictures)ModerateEvery image must depict the node's concept. Filler ornament is out.
Distinctiveness works by contrast: an item stands out from its neighbours (the isolation effect)ModerateArt is for chosen subtrees and key nodes. If every node is elaborate, none stands out. A restrained base style with a few rich nodes works better than uniform richness.
Decorative detail around the content can hurt learning, and experts can be hurt by redundant picturesModerateArt must be switchable off, and a lean mode must show vector nodes only.
The label should touch the image and not repeat what the image already saysModerateThe engine draws the keyword next to or on the picture, and the image contains no text.
Making or reworking a map helps more than viewing oneStrongThe user chooses and edits the art. Generation supports this and does not replace it (decision D-18).
AI-generated node images improve recallWeakNo controlled study was found. One 2025 study on kanji, seen only as a search summary, reported that AI mnemonic illustrations did not clearly improve short-term recall but lowered cognitive load Kanji study.

Two practical cautions come from outside the memory literature. A 2025 pilot by Jisc found that AI-generated images often contained inaccurate or inconsistent elements, that text in images was weak, and that defaults leaned towards Western stereotypes Jisc 2025. Medical students report using picture mnemonics for concrete facts and maps for relationships, and the notes found no independent critique of symbol overload.

Decision

Artwork is opt-in per subtree, depicts the meaning of each node, aims for distinctness among siblings, spends its richest treatment on few key nodes, and can be switched off for the whole map with one control. The report does not claim a percentage memory gain for AI pictures.

Not verified

There is no direct evidence on AI-generated node images in mind maps. The product treats them as ordinary pictures with no assumed generation benefit, and the user's belief that art makes maps easier to remember is a hypothesis the app can help test through the recall features (features page).

The user experience

The flow is built around one rule: show a small, cheap sample first and spend the whole batch only after the user approves it. Generating one image took about 12 seconds in the hands-on test, so a rejected 20-image batch wastes several minutes of waiting and an unknown share of the user's rate limit.

  1. Select. The user selects a subtree root and chooses Picture or SVG from the context menu, the format panel or a shortcut, with a scope: this node only, the whole subtree, or chosen levels. This follows the Xmind pattern of changing the format of one selected branch.
  2. Style. The dialog shows the style sheet that will apply: inherited from the nearest art ancestor, a preset, or a custom sheet. Presets offer previews.
  3. Sample. The app generates one or two nodes (for pictures, the root and one leaf) and shows them in place on the map. The user accepts, edits the style or tries again.
  4. Batch. After the user accepts, the remaining nodes are queued. The dialog shows the count, an estimated time and the rate-limit meter. Each node shows its vector form with a progress state until its art arrives, then swaps without moving neighbours.
  5. Refine. The user can regenerate one node, edit its prompt, replace its image, change the style sheet (which marks all art stale and offers a batch), or revert the subtree to vector.

What happens when the map changes

Text edited
The old art stays visible with a stale marker, and the node offers regeneration. Nothing is regenerated automatically, because a silent image change would break the user's mental picture and spend rate limit.
Node added
The new node shows in vector form inside the art subtree, with an action to generate its art in the subtree style.
Node moved or reparented
Art stays valid. Moving a node into a different art subtree marks it as belonging to the new subtree and offers to regenerate it in that style.
Style sheet edited
All art in the subtree is marked stale; the user chooses to regenerate all, regenerate selected nodes, or keep the old art.
Revert
One undo step returns to vector with no loss of assets.
Idea for Radiant

The brief that Radiant builds for each node (node text, path of ancestors, siblings, style sheet) should be visible and editable, as in the Xmind feature that drafts a prompt from the topic and its surrounding map and offers a re-roll Xmind docs. Editing the brief is the cheapest way for the user to take part in generating the art, which matters because the learning evidence favours user effort.

Proposed design The field list combines the style fields in the engine notes (palette, medium, line weight, mood, reference image, negative prompts, seed) with two additions drawn from practice. The first is a recurring cast and symbol vocabulary. Sketchy, the picture-mnemonic product for medical students, describes recurring symbols, a recurring cast and a separate setting for each unit, in its own marketing text Sketchy blog. A setting per main branch and a symbol dictionary per map follow that pattern. The second is a rule against stereotyped defaults: the sheet fixes the cast, and avoids realistic humans, because the Jisc pilot found stereotyped defaults.

Reference image first

For picture subtrees the first call generates a reference image in the sheet's style, and the user accepts it or asks for another. Every later call attaches it. The hands-on test attached a reference image to a request and received a transparent PNG, and the model's rewritten prompt said to match the supplied reference closely. Exactly what was tested is narrow.

Presets

The app ships presets as editable copies. A Buzan preset follows the visual-traits checklist from the practice research: a central image, vivid colours with one colour per main branch kept in the same family down the branch, images where they help and not on every node, a consistent simple-sketch style, one keyword per node, and no text inside images. The notes record that guides disagree about colour (Buzan wants vivid, Foreman wants light, Xmind's article advises low saturation), so the app offers presets and not one rule Foreman IQ Matrix Xmind blog. Other presets cover sketchnote (hand-drawn wobble, supported by Rohde's stance that sketchnotes capture ideas and are not about art), flat vector with low saturation, and a quiet monochrome for lean mode.

Picture subtrees

In a picture subtree every node is one generated image with a transparent background, with the keyword drawn by the engine (decision D-10). The pipeline runs in the host process and follows five steps.

  1. Brief. The brief builder composes a prompt from the node text, the ancestor path, the sibling list and the style sheet.
  2. Generate. A thread asks Codex's built-in image tool for the image, with the reference image attached.
  3. Ingest. The host decodes the returned PNG, checks for alpha, removes the background locally if needed, trims and pads, and measures.
  4. Anchor. The host derives default anchors from the subject mask and stores them with the asset.
  5. Place. The engine updates the node's box, lays out the subtree incrementally and swaps the placeholder for the image.

Rules for memorable images

These rules come from general mnemonic principles and from the evidence summary, not from a tested prompt library. The engine notes record that no source on mnemonic image prompts was fetched, so every rule below is a Proposed design to be checked in the spike.

  • One concrete subject. The image shows a single object or scene that depicts the node's meaning. Abstract concepts are shown through a concrete stand-in (for names and arbitrary facts, a sound-alike or transformed picture, as the mnemonic literature describes).
  • Exaggerate or interact where it helps. Unusual scale or an interaction between the subject and the neighbouring concept can aid recall. The effect is moderate for emotion and untested for humour, so the brief uses it sparingly and on key nodes.
  • Distinct from siblings. The brief lists sibling subjects and asks for a different silhouette, colour emphasis or object type for each.
  • No text in the image. The brief says "no text, no letters", and the engine draws the label.
  • Simple, transparent background. No scenery unless the style sheet says the branch has a setting.
  • Order cues stay outside. Numbers and arrows for ordered content are drawn by the engine, since unusual images can otherwise hide sequence.

Generation, timing and batch size

Image generation works through the ChatGPT login with no API key. The request is plain prompt text; the model decides to call its image tool. The result comes back as inline base64 PNG data, together with a saved path and the revised prompt the model wrote.

Verified hands-on Two single samples give 12 to 29 seconds per image, so a sequential batch of 20 images would take roughly 4 to 10 minutes. The tests did not try several images in flight at once, and whether Codex allows parallel image jobs, or whether parallel jobs share one rate-limit meter, is unknown. The plan is therefore: one image at a time by default, the sample-first flow to avoid wasted batches, a concurrency setting raised only after a spike measures it, and a progress display that shows each node's state. A batch of more than a configurable number of images (default 10) asks for confirmation with the count and current rate-limit meter. The cost per image against the user's plan is Unverified.

Codex also saves its own copy of every generated image under its home folder. The host copies the returned data into the document store and does not rely on that copy.

Transparency, trimming and storage

Verified hands-on A request for a transparent background with a reference attached returned a real RGBA PNG whose corner pixel was almost fully transparent. The OpenAI reference lists transparent background support for some image models (in preview for the newest) and says it needs PNG or WebP output, and a community post reports that transparency sometimes did not come back OpenAI reference. One sample worked and the client cannot set the parameter directly, so the host keeps local background removal as the fallback (decision D-10) and checks the alpha channel of every result. After ingestion the host trims transparent margins, adds padding, records the aspect ratio, creates a thumbnail and a compact blurred placeholder, and stores the asset by content hash with the prompt, revised prompt, model and style sheet version. GPU blending uses premultiplied alpha so soft cut-out edges do not show halos (engine page).

Connecting pictures to branches

Proposed design The notes found no prior art for joining generated images to a branch network, so this is a design to test. The connection must look seamless, work with any image the model returns, and stay editable.

  • Branch under the image. The engine draws the branch to the in-anchor, beneath the image. The image's soft alpha edge covers the join. This works with any generated image.
  • Declared anchors. Each image box carries normalised in and out anchors, set by the host after generation (for example by finding the subject mask and choosing the nearest edge points to the parent and the children) and stored in the document. The user can drag them.
  • Stem and colour. A short stem drawn in the branch's style bridges any remaining gap, and the branch colour is matched to a palette entry of the style sheet.
  • Generating the connector inside the art is the least reliable option and is avoided.

The label has three placements. On the branch, the label sits on the line next to the image, which follows the Buzan advice that text sits on the line. As a caption, it sits under the image. In recall mode it is hidden until hover, so that the picture alone prompts recall (recall features, decision D-18). The label stays in one place for a node unless the user changes the mode.

Not verified

How good automatic anchors are on real generated images is unknown. The engine notes suggest nearest-edge detection on the subject mask but did not test it. The spike should measure how often the default anchor needs a manual fix.

SVG subtrees

In an SVG subtree the order is layout first, artwork second (decision D-11). The engine computes the box of every node, then asks the model for SVG that fills those boxes under a strict contract. The engine validates and sanitises the result, draws the connectors itself between the declared anchors, and hides node groups to collapse. Only the engine's own layout decides where nodes go, so editing and collapsing behave as in a vector map.

Root elementOne svg element with a viewBox equal to the frame given in the request, in user units. No width or height beyond the viewBox.
Node groupExactly one g per node, with id="node-ID" where ID is the node's id in the request. No other top-level groups except an optional defs.
BoxAll drawing in a node group must lie inside the node box given in the request. The engine computes the real bounding box and checks it.
data-anchor-inRequired. The point "x,y" in viewBox units where the incoming branch should end. It lies on or within a few units of the group boundary on the side nearest the parent anchor. For the subtree root it is where the parent's branch arrives.
data-anchor-outRequired for a node that has children and omitted for a leaf. The point where the child branches start, on the side nearest the children. It must differ from the in-anchor by at least a minimum distance (a proposed starting value is one quarter of the box diagonal). Equal points fail validation.
ConnectorsForbidden. No line, path or group whose purpose is to link one node to another. The engine draws all connectors from out-anchors to in-anchors.
TextForbidden: no text, tspan or glyph outlines that spell words. The engine draws labels.
Forbidden contentNo script, foreignObject, image, use with an external reference, style with imports, event attributes, animation elements, or any external reference.
Allowed elementssvg, g, path, rect, circle, ellipse, line, polyline, polygon, defs, linearGradient, radialGradient, stop, clipPath, mask, title, desc, plus transform, fill, stroke and opacity attributes. Filters only from a short allow-list, and none by default.
Element budgetA cap per node group and a cap per subtree. Starting values to tune in the spike: 40 drawing elements per node and 400 per subtree. The test file had 17 paths for five nodes against a prompt limit of 60.
PaletteOnly the colours listed in the request, which come from the style sheet.

The allowed element list comes from the engine notes' recommended subset. The notes also cite resvg as a strict static renderer that excludes scripts and animation, DOMPurify for restricting a document to SVG profiles, and note that text needs a font and so is best left to the engine resvg DOMPurify.

A short conforming example for a root with one child (colours as HSL values; the request lists the real palette):

<svg xmlns="http://www.w3.org/2000/svg" viewBox="0 0 800 400">
  <g id="node-n1" data-anchor-in="40,200" data-anchor-out="240,200">
    <rect x="40" y="150" width="200" height="100" rx="30"
          fill="hsl(38 60% 88%)" stroke="hsl(20 45% 22%)" stroke-width="4"/>
    <path d="M110 205 H170 V222 C170 238 160 244 140 244 C120 244 110 238 110 222 Z"
          fill="hsl(28 55% 35%)"/>
    <path d="M128 196 C121 186 133 185 127 176" fill="none"
          stroke="hsl(12 75% 52%)" stroke-width="4" stroke-linecap="round"/>
  </g>
  <g id="node-n2" data-anchor-in="360,110">
    <rect x="360" y="60" width="200" height="100" rx="30"
          fill="hsl(38 60% 88%)" stroke="hsl(20 45% 22%)" stroke-width="4"/>
    <circle cx="460" cy="110" r="34" fill="hsl(32 60% 60%)"/>
  </g>
</svg>

The engine then draws a branch from (240,200) to (360,110). The example has no connector, no text, a distinct out-anchor on the root, and no out-anchor on the leaf.

Validation, sanitising and repair

  1. Parse. A strict parser reads the file and rejects malformed XML.
  2. Sanitise. The allow-list removes disallowed elements and attributes and external references, and the sanitiser report is stored with the asset.
  3. Check the contract. The engine checks the node groups, anchors, boxes, budgets and palette.
  4. Repair. If a check fails, the engine re-prompts with the specific failure (for example "node-n3 has equal anchors") for a bounded number of retries. If a group is outside its box, a scale-to-fit step corrects it first.
  5. Fall back. If the retries fail, the affected nodes use the vector form and show a retry marker. The rest of the subtree still renders.

A render-check-repair loop with the parser's error fed back is documented for generated diagram code in one project, which raised validity from about 70 per cent to nearly 100 per cent HU Berlin. That is Mermaid code, not SVG, and a single project, so it is a precedent for the loop and not a forecast of the SVG success rate.

Rendering and collapse

The app uses the browser engine to render SVG, because generated SVG can use gradients, clipping and filters that the small native SVG libraries do not support (decision D-12). Visible SVG subtrees are rasterised to textures per zoom bucket, and a live inline SVG is shown only for the node being inspected closely. Collapse works by hiding groups: the engine hides the groups of descendants, shows a count badge on the parent group, and animates the groups with transforms. Because the engine caches textures per node group and not per subtree, collapse needs no re-rasterisation of the remaining groups (engine page).

FR-ART-33Must

Layout first

The engine must compute all node boxes of an SVG subtree before requesting art, and must pass each node id, box and role to the model.

Accept when: The request payload lists every node box and the generated groups lie in the boxes. Why: Decision D-11.

FR-ART-34Must

Node group contract

Valid SVG must contain one group per node with the id pattern node-ID, a viewBox equal to the requested frame, and no other top-level groups.

Accept when: A file with a missing node group is rejected by the validator with the node id named. Why: Contract passed in one test sample.

FR-ART-35Must

Anchor semantics

The in-anchor must be the point nearest the parent anchor and the out-anchor the point nearest the children; for a node with children the two must differ by at least a minimum distance, and both must lie on or near the group boundary.

Accept when: A group whose two anchors coincide is rejected when the node has children. Why: Four of five anchors coincided in the test.

FR-ART-36Must

No connectors and no text

The validator must reject connector groups, text and any element that draws a line from one node group to another; the engine must draw all connectors.

Accept when: A file with a connectors group fails validation. Why: The model drew its own connectors in the test.

FR-ART-37Must

Allow-list sanitising

The sanitiser must allow only a fixed element and attribute list, remove scripts, event attributes, external references, embedded images and foreign objects, and must run before any rendering. It must also enforce a per-node and per-subtree element budget and the palette limit.

Accept when: A file containing script, an external image reference and an event attribute is cleaned or rejected with each issue reported. Why: DOMPurify restricts to SVG profiles.

FR-ART-38Must

Repair loop

On a validation failure the app must re-prompt with the specific failure, retry up to a configured number of times (default two), and then fall back to the vector form for the affected nodes.

Accept when: After two failed repairs the nodes show vector form and a failure marker. Why: Single-project parse, check, repair precedent; HU Berlin.

FR-ART-39Should

Per-node regeneration

The app should regenerate one node group with neighbours as context and splice it into the stored SVG, re-validating the whole file.

Accept when: Regenerating one group leaves all other groups byte-identical. Why: Partial regeneration.

FR-ART-40Should

Texture per zoom bucket

Visible SVG subtrees should be rasterised to textures per node group and zoom bucket, and shown as live inline SVG only while one is inspected closely.

Accept when: Collapsing a node in an SVG subtree does not re-rasterise the remaining groups. Why: Decision D-12; engine.

Layout stays stable (decision D-13). When a new image has a different aspect ratio, the node box changes and the subtree re-lays out with animation, and no unrelated subtree moves. Failure, storage and export

Failures are certain in a pipeline that depends on a remote model, so the design makes them cheap. The vector form always exists in the document, so no failure can leave a map unusable (decision D-09).

Failure cases and responses
CaseResponse
One generation failsThe node keeps its vector form and shows a failure marker with a retry action; the batch continues.
Rate limit reached mid-batchThe queue pauses, finished nodes stay, the reset time is shown when the service gives it, and the user resumes. The Codex app-server reports rate-limit state and has error types for limit exhaustion, but the exact live error was not triggered in the test (Codex page).
Invalid SVGRepair loop, then vector fallback for the affected nodes.
Image without alphaLocal background removal; if that fails, the image is shown in a rounded frame.
Stale artKept and marked; regeneration is offered.
OfflineExisting art displays, edits and exports normally; only generation is disabled.
Corrupt assetThe vector form shows and the error is logged.

Storage and export

Assets are stored content-addressed in the document's SQLite file with their prompt, revised prompt, model, style sheet version and input hash (decisions D-14 and D-19). Exports render picture and SVG subtrees faithfully to PNG, SVG and PDF. Text exports (Markdown outline, OPML, JSON) always carry the node text. SVG export is a selling point, since generated art that can be edited in another tool has precedent in Napkin AI's SVG export, and vtracer, an open tool that converts a raster image to SVG, could later turn a flat-style picture into SVG artwork that the engine then wraps in the node contract vtracer. The conversion is an idea from the engine notes and is not tested.

Vector is always available

A subtree must never be left without a usable representation: any failure must leave or restore the vector form.

Accept when: Every failure test in this section ends with a usable, editable subtree. Why: Decision D-09.

When the rate-limit meter or an error says a limit was reached, the queue must pause, keep finished work, show the reset time when given, and resume on user action.

FR-ART-49Must

Assets must be stored content-addressed in the document store and referenced from nodes with an input hash so that unchanged inputs reuse the stored asset.

Export to PNG, SVG and PDF must render picture and SVG subtrees faithfully, and SVG export must embed vector art as vector elements and pictures as embedded images.

Accept when: The exported PNG matches the on-screen map for a mixed test map. Why: Napkin precedent for SVG export.
