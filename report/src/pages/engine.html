Canvas engine: design and requirements

The engine is a pure, portable core that owns the tree, the layout and the geometry, a small WebGL2 renderer that draws the result, and the browser engine, which supplies SVG rasterisation and text input. Measurements on your Mac show large headroom for this split: a batched WebGL2 scene held 120 frames per second with 100,000 branches, about twenty times the 5,000-node large reference map. This page explains the design, names the algorithms and sources behind it, and states 40 numbered engine requirements.

They are described in full on the stack page and in the quality page, which owns the performance requirements. Not measured: Electron or Chromium, input latency, SVG rendering, real content, real text layout, hit-testing and editing. The design below therefore treats the measurements as evidence that the renderer will not be the bottleneck, and treats everything else as design to be confirmed in the first milestone spikes.

Implication for Radiant

Three decisions shape this page. The engine core is plain TypeScript with no browser or GPU dependencies (decision D-05), so it can run in a worker and later be ported piecemeal. The renderer is a small purpose-built WebGL2 layer behind a narrow interface (D-04). SVG artwork and text editing use the browser engine (D-12, D-03). The tree remains the single source of truth and pictures and SVG are only representations of it (D-09). Picture and SVG subtree behaviour is specified on the art subtrees page; user-facing canvas features are on the features page.

Architecture

The engine is a stack of eight layers. The upper layers know nothing about the screen; the lower layers know nothing about the document. The rule that makes the split useful is the dependency direction: a layer may depend only on layers above it in the list, and the first four layers must run unchanged in a web worker and in a plain Node test process.

1. Document model and operation logNodes with stable ids, edges, styles, asset references, and the list of edit operations with their inverses. Runs in the main thread or a worker. Must not depend on the DOM, the GPU, layout results or the file store.
2. Layout engineComputes a position for every visible node from node boxes, sibling order, the per-branch layout variant and the stored seed. Runs in a worker over compact arrays. Must not depend on rendering, fonts loaded in the page, or asset decoding; it receives sizes as numbers.
3. Geometry and tessellationTurns branch centrelines and width functions into closed outlines and triangles, and places glyphs along curves. Runs in a worker. Must not depend on WebGL objects; it emits typed arrays.
4. Spatial index and hit-testingBounds index for culling and exact outline tests for picking. Runs where the geometry lives (worker, with a read-only copy or query messages for the main thread). Must not depend on the renderer.
5. Scene and level of detailBuilds the per-frame draw list from the visible set, the camera and the zoom, choosing full, reduced or stand-in drawing per item. Runs on the main thread because it must read the camera each frame. Must not mutate the document.
6. Renderer backendsThe WebGL2 backend (a handful of batched draw calls) behind a narrow interface; a WebGPU backend later. Runs on the main thread (or an offscreen canvas in a worker if that is later measured to help). Must not know about nodes, only meshes, quads and uniforms.
7. Asset pipelineDecoding, thumbnail pyramids, placeholders, texture residency, SVG sanitising and rasterisation per zoom bucket. Decoding and rasterisation run in workers; texture upload on the main thread; heavy image work (thumbnails, background removal) in the Rust host (decision D-06). Must not block a frame.
8. Host bridgeThe single host interface for the SQLite store, the Codex process, file dialogs and export. Runs in the Rust host process (decision D-01). The front end must not import the shell library anywhere else, so Electron remains a days-not-months swap.

The flow in the figure is a proposed design (Proposed design) that follows the layer list the research notes sketch. Two supporting facts come from published engines. tldraw documents level-of-detail rendering by zoom and on-screen size, reactive state that tracks dependencies automatically, and an R-tree spatial index for brush and erase tools tldraw perf tldraw 4.4. Figma's renderer is C++ compiled to WebAssembly, sits behind an interface layer that maps closely to WebGL, uses WebGPU with a mid-session fallback to WebGL, and batches uniforms into one buffer Figma blog. Both support the same shape: a spatial index, level of detail, a GPU renderer with a thin backend interface, and a fallback path.

Decision D-05 says to start in TypeScript and port only measured hot spots. The layers most likely to move are layout and tessellation, which are numeric loops over arrays. Decision D-16 keeps Zig as a candidate for exactly this kind of small kernel compiled to WebAssembly; see the Zig page. Writing the layers as functions over typed arrays, with no object graphs crossing the boundary, is what keeps that port cheap.

Risk

The 120 fps result depends on a private WebKit flag. The engine must therefore pace itself from the refresh interval it actually observes, not from an assumed 120 Hz, and must meet its work budget at 16.7 ms as well as 8.3 ms. WebKit bug 294338 asking for a public API is still open WebKit 294338.

ENG-01Must

Pure engine core

The document model, operation log, layout, geometry, tessellation, spatial index and hit-testing must be TypeScript modules with no import of DOM, canvas, WebGL, Tauri or Node-only APIs.

Accept when: the core test suite runs unchanged in a Node process and in a web worker, and a build check fails if any core module imports from the renderer, asset or host packages. Why: keeps a later port to Rust or Zig and a native-shell fallback open (decisions D-05, D-17).

ENG-02Must

Narrow renderer and host interfaces

All GPU work must go through one renderer interface that speaks in meshes, quads, glyph quads and uniforms, and all native calls must go through one host interface. No other module may import the shell library or call WebGL directly.

Accept when: a headless test renderer implementing the interface passes the same scene tests as the WebGL2 backend, and a search of the source finds the shell library imported in exactly one module. Why: allows a WebGPU backend, PixiJS fallback or Electron shell without touching the engine (decisions D-01, D-04; see the stack page).

ENG-03Must

Heavy work off the main thread

Layout, tessellation, SVG rasterisation and image decoding must run off the main thread, and the main thread must receive only finished typed arrays or bitmaps.

Accept when: on the 5,000-node reference map, main-thread script time per frame during continuous pan and zoom is at most 4 ms, measured over a 10-second run, and stays within the 8.3 ms frame budget at 120 Hz. Why: the budgets in the quality page; Canvas2D already used 3.5 ms of script per frame unculled in the spike.

Layout

Layout is the part of the engine that decides where every node goes. The recommended base is a non-layered tidy tree for variable-size nodes (decision D-13), with two-sided, radial, top-down and outline-like variants chosen per main branch, and an organic treatment on top that is seeded so it is reproducible. The model never decides layout (decision D-08).

The tidy-tree lineage

The standard lineage starts with Reingold and Tilford (1981), continues with Walker (1989 and 1990) and Buchheim, Juenger and Leipert (2002, linear time), and reaches van der Ploeg (2014). The first three are cited through the d3-flextree README d3-flextree; the research could not fetch the Walker and Buchheim full texts, so their details are not repeated here.

Variable node sizes are the deciding factor. A picture node's box is its image bounds plus caption plus padding, and an SVG node's box is the one the engine reserved for its artwork. Fixed-size variants of the older algorithms cannot express that, so the van der Ploeg and flextree family is the right base (the notes' inference).

Two-sided balancing and other variants

Proposed design For a two-sided map in the style of Xmind or MindNode, split the root's children into a left set and a right set, run the tidy layout on each half and mirror the left. Balance by total subtree extent (the sum of the children's heights) with a greedy or partition pass, not by child count, because one child with a hundred descendants outweighs five leaves. The notes found no primary source for this and no published treatment of left-right balancing, so it is the common approach rather than a cited one.

Proposed design For radial maps, map the layout's abstract depth and breadth coordinates onto radius and angle, with the angular wedge of each subtree proportional to its leaf weight, which is the "abstract coordinates" idea in the d3-flextree README. Wide pictures need a ring radius chosen from the largest node on that ring. Top-down and outline-like variants reuse the same engine with the axes swapped or the sibling gap changed. Because each main branch stores its own variant, one map can mix a radial cluster with an outline-like branch.

Mental map and stability

Misue, Eades, Lai and Sugiyama (1995), "Layout Adjustment and the Mental Map" (Journal of Visual Languages and Computing 6(2)), introduced the idea that an edit should not scramble the arrangement the user has learned, and includes a method to remove node overlaps while preserving it Misue 1995. Later work includes simulated-annealing-based mental-map-preserving drawing NYCU paper. For a memory-oriented app this matters more than usual: the Buzan page and the science page cover why a memorable map matters.

Proposed design Stability rules built on that literature: keep a cached position per node; re-lay-out only the changed subtree and the siblings it displaces; when a node is collapsed or expanded, keep the clicked node fixed on screen and translate everything else relative to it; store manual placements as offsets from the automatic position so they travel with their parent; and always lay out with the final box size, or a reserved placeholder box from the declared aspect ratio, so a picture arriving later does not move anything.

Manual offsets and animation

MindNode stores manual moves as offsets from the automatic position, and decision D-13 adopts the same model. The stored offset is relative to the node's own automatic position, so changing the tree above it moves the node with its parent and keeps its relation to the parent. Changes animate by interpolating old to new positions per node. The notes suggest roughly 200 to 300 milliseconds with per-node easing (the report's recommendation, not a measured preference). Layout itself runs in a worker over a compact structure-of-arrays tree and posts positions back. The notes did not benchmark flextree at 10,000 nodes; the 50 ms budget for 5,000 nodes in the decisions brief is a target to confirm in the first spike.

Organic layout

Not verified

The notes found no published algorithm and no open-source implementation of Buzan-style organic layout (the curved, fanning, hand-made look of iMindMap). Everything in this subsection is the report's own design.

Proposed design Take the collision-free tidy skeleton as the starting point, then: (1) convert each parent-to-child edge into a cubic Bezier whose tangent at the parent follows the parent's incoming direction, so branches fan out smoothly; (2) bend each branch by a per-node angle offset derived from a hash of the node id and a document seed, never from a random number generator at draw time, in the same spirit as the seed option of rough.js rough.js; (3) run a few passes of overlap removal that displace overlapping boxes in the manner of Misue 1995; (4) store the result as cached positions that are derived data, not truth. Main branches at depth one carry the colour, and curvature and thickness fall with depth. Because the jitter is a pure function of id and seed, reloading the file or re-running layout gives the same picture.

ENG-04Must

Non-layered tidy layout with per-node boxes

The default layout must be a linear-time non-layered tidy tree (van der Ploeg 2014) that accepts a width and height per node and a spacing function, and never lets two node boxes overlap.

Accept when: on the small (200 nodes) and large (5,000 nodes with 300 pictures) reference maps, with randomly sized boxes, a test finds zero overlapping box pairs, and the output matches the d3-flextree result on the same tree within floating-point tolerance. Why: variable-size picture and SVG nodes; see art subtrees.

ENG-05Must

Layout time budget

A full layout of the large reference map must complete off the main thread within the budget, and an edit to a single subtree must re-lay-out only what it affects.

Accept when: a full layout of 5,000 nodes takes under 50 ms in the worker (median of ten runs), and the 50,000-node stress map completes without blocking the main thread for a frame. Why: budget from the decisions brief, to be confirmed in the spikes (target proposed by the report).

ENG-06Must

Deterministic layout

Layout must be a pure function of the document structure, node boxes, per-branch variants, stored offsets and the stored seed. It must not use the clock, an unseeded random source or iteration order of unordered collections.

Accept when: laying out the same document twice, and again after a save and reload, yields identical positions, and the same result in the worker and on the main thread. Why: reproducible organic layouts and stable exports (decision D-13).

ENG-07Must

Stable, animated edits

Editing, collapsing or expanding inside one subtree must not move nodes in unrelated main branches, and the node the user acted on must keep its screen position. Position changes must animate and must not drop frames.

Accept when: after an edit inside one main branch of the large map, every node of the other main branches has zero displacement, the acted-on node moves by less than one device pixel on screen, and frames during the transition stay within the 8.3 ms budget at 120 Hz (16.7 ms at 60 Hz). Why: mental-map preservation (Misue 1995) and decision D-13.

ENG-08Must

Two-sided balancing by subtree extent

The two-sided variant must assign root children to the left and right by cumulative subtree extent and must be recomputed only when the user adds or removes a main branch, so existing sides do not flip on unrelated edits.

Accept when: on a test map with one very large and five small main branches, the difference between left and right total extent is smaller than the largest main branch, and adding a deep descendant inside one branch changes no branch's side. Why: MindNode-style maps; proposed design without a published source.

ENG-09Should

Layout variant per main branch

Each main branch must store its own layout variant (two-sided, radial, top-down or outline-like) and the engine must lay out each branch with its variant while keeping all branches free of overlap with one another.

Accept when: a map with one branch in each variant lays out with zero box overlaps, and switching a branch's variant leaves other branches' positions unchanged. Why: decision D-13 and the variants in the layout features.

ENG-10Must

Manual offsets from automatic position

A manual node move must be stored as an offset from that node's automatic position, not as an absolute coordinate, so the node follows its parent when the layout changes.

Accept when: after dragging a node, then moving its parent by editing a sibling above it, the dragged node's offset value in the file is unchanged and its position relative to its parent is unchanged. Clearing the offset returns the node to its automatic position. Why: MindNode precedent, decision D-13.

ENG-11Must

Reserved boxes for pending assets

A node whose picture or SVG is pending must be laid out with a reserved box derived from the declared aspect ratio, and the arrival of the asset must not change any node position unless the actual box size differs from the reservation.

Accept when: replacing 300 placeholders with decoded images of the reserved sizes in the large map produces zero position changes in a layout comparison. Why: the layout must not shift while generation streams in (see the AI engine page and art subtrees).

ENG-12Should

Seeded organic treatment

The organic style must derive every random-looking quantity (branch bend, wobble, curvature) from a hash of the node id and the document seed, and must store only the seed, never the derived values as truth.

Accept when: two machines opening the same file draw identical branch outlines, changing the seed changes the picture, and a search of the code finds no unseeded random call in layout or geometry. Why: proposed design; reproducibility (decision D-13).

Branches

A branch is a cubic Bezier centreline with a width that tapers from thick at the parent to thin at the child, drawn as a filled closed outline. The report recommends building that outline on the CPU, caching it per branch, and uploading all visible branches as one mesh. The spike shows the GPU side is far from the limit: 100,000 pre-tessellated branches of 24 triangles each, drawn in a single call, held 120 fps.

What stroke research offers

Levien and Uguray, "GPU-friendly Stroke Expansion" (HPG 2024, Best Paper third place; PACM CGIT 7(3)), approximate cubic Beziers with Euler spiral segments, lower the offset curves to lines or circular arcs, avoid recursion, introduce a new error metric and build on Nehab (2020) Levien 2024 paper page. It is the state of the art for expanding strokes on the GPU every frame. A mind map has thousands of branches that change only on edits, so the notes judge CPU tessellation, cached per branch, to be enough, and Euler-spiral expansion to matter only if stroking must run on the GPU each frame. The authors list imperfect load balancing as a limitation of their approach.

The notes did not fetch the kurbo documentation, so the claim that kurbo has no variable-width stroke is not verified here; the nanoui library discussed on the Zig page also lacks variable-width strokes (decision D-16). Vello now includes three renderers (the compute-centric original, Vello GPU and Vello CPU, with a WebGL2 and wgpu backend for the GPU one) Vello, which makes it a reference for a later native path rather than a dependency for the web renderer.

perfect-freehand shows the simplest workable approach: input points, optionally with pressure, become a closed polygon outline, with thinning mapping pressure to width and taper options at the start and end. Self-crossings remain unless flattened with polygon-clipping, and the lower-level functions getStrokePoints and getStrokeOutlinePoints are exposed perfect-freehand. tldraw uses it for pen shapes according to its author discussion 38. rough.js adds the hand-drawn look with roughness, bowing and a seed for reproducibility rough.js.

The recommended branch pipeline

  1. Centreline. One cubic Bezier from the parent's attach point to the child's in-anchor, with the tangent at the parent following the parent's direction.
  2. Width function. w(t) falls from the parent's width at the attach point to a thin end; the width at t = 0 equals the parent's width where the child leaves it.
  3. Outline. Sample the centreline, offset by half the width along the normal on both sides, add caps, and emit one closed polygon.
  4. Triangles. Triangulate into a strip or indexed triangles and append to a per-style batch.
  5. Cache. Rebuild only branches whose endpoints, widths, seed or style changed.

Proposed design The whole pipeline is the report's design, assembled from perfect-freehand's outline idea and the cubic-plus-width model; no source describes it for mind maps. Triangle strips render cheaper, but a filled closed outline is easier to give textures, outlines and rough edges, so filled outlines with an optional second pass for texture are the recommended choice.

Joins and wobble

Proposed design Where several children leave one parent, each child branch starts slightly inside the parent's outline and is drawn before the parent (or merged into it), so the join shows no gap or seam. The same rule serves picture and SVG subtrees: the engine draws the parent branch to the node's declared in-anchor under the image, and the image's soft alpha edge hides the join. Seeded wobble moves the centreline sample points by a hash of the node id and the seed, so a hand-made look never changes between sessions. Batching puts every branch of a style into one mesh, so the number of draw calls does not grow with the number of branches.

ENG-13Must

Tapered closed-outline branches with matched joins

Each branch must be generated as a closed outline from a cubic centreline and a width function, whose start width equals the parent's width at the attach point and which begins inside the parent's outline.

Accept when: a visual regression test of a parent with eight children shows no gap or seam at the join at three zoom levels, and the child's start width differs from the parent's by less than one device pixel at each. Why: seamless branches (proposed design); same rule is required at picture and SVG anchors, see art subtrees.

ENG-14Must

Batched, cached branch meshes

Branch meshes must be cached per branch, rebuilt only when the branch's inputs change, and drawn in per-style batches so that the draw-call count for branches does not depend on the number of branches.

Accept when: the draw-call count for branches is the same on the small and the large reference maps; rebuilding the meshes of all 5,000 nodes takes no longer than the spike's measured 7 ms for 10,000 branches (synthetic, 12 segments each); and an edit to one branch rebuilds only that branch. Why: 100,000 batched branches held 120 fps in the spike; the cost lies in rebuilds, not drawing.

ENG-15Must

Hit-testing against outlines

Picking a branch must test the branch's outline polygon after a bounds-index prefilter, and picking a node must use its box or its representation's hit shape.

Accept when: a click on the thin end of a tapered branch selects it, a click within its bounding box but outside the outline does not, and a pick on the large map fits inside the 4 ms script budget. Why: bounds alone select the wrong object on curved branches (the notes' inference).

Text

Engine-drawn text is rendered on the GPU from a glyph atlas, laid horizontally by default and along the branch only where the branch is gentle enough. Editing uses a real HTML text field placed over the node, so input methods, accessibility and the system caret all work.

Text along a branch

Proposed design Shape the string with a text shaper (HarfBuzz is the notes' suggestion) to obtain glyph advances, then place each glyph at an arc length s along the centreline, rotated to the tangent and offset to the branch centre or edge. The constraints that make it legible are: reject or shorten a label if the radius of curvature falls below a threshold relative to the font size; reverse the path direction if the text would otherwise run upside down; and fall back to a horizontal label beside the branch when the branch is too short or too curved. The keyword is always engine-rendered text, never baked into a generated image.

The limit is script. Per-glyph placement assumes each glyph is an independent shape. Scripts whose letters join or reshape according to neighbours (Arabic is the usual example), and scripts with complex vowel marks, cannot be cut into independently rotated glyphs without breaking the writing, so the proposed rule is that they always take the horizontal fallback. The notes did not research SVG textPath, which would be the DOM-side equivalent, or glyph caching; both remain open.

Inline editing

When the user edits a label, the engine places a real HTML text field exactly over the node's box, matching font, size and zoom, and removes it on commit. The field gives the operating system's input methods, dead keys, spelling, selection behaviour and accessibility tree for free, none of which a canvas can reproduce. This follows decision D-03, which keeps ordinary HTML for text editing and accessibility.

ENG-16Must

Crisp GPU labels at every zoom

Labels must be drawn by the engine from a multi-channel distance-field atlas (or an equivalent that stays sharp when magnified) and must remain crisp from the minimum to the maximum zoom, on both 1x and 2x displays.

Accept when: a visual test at a device pixel ratio of 2 shows no blur on 2,000 labels, the shader's screen pixel range is at least 2 at the zoom where a label is drawn at all (never below 1), and 2,000 labels draw at 120 fps in the scene that held 100,000 branches. Why: msdfgen guidance; 2,000 labels held 120 fps in the spike with a soft 1x atlas.

ENG-17Should

Legible text along a branch

Where a label is set along a curve, the engine must never draw it upside down, must refuse curvature above a configured limit relative to font size, and must fall back to a horizontal label for short or sharply curved branches and for scripts that cannot be split into independent glyphs.

Accept when: a test over a sweep of 360 branch directions finds zero upside-down labels, and the test corpus of Arabic and Devanagari labels always renders in the horizontal fallback. Why: proposed design; legibility rules from the notes.

ENG-18Must

Inline editing through a real text field

Editing a node's text must use an HTML text input or contenteditable element positioned over the node, with the same font metrics, and must hand back to the canvas on commit or cancel.

Accept when: Japanese or Chinese input method composition completes correctly, VoiceOver reads the field and its content, and the text field's position matches the drawn label within one device pixel at three zoom levels. Why: input methods and accessibility cannot be built on a canvas; decision D-03; accessibility targets are on the quality page.

Evidence

Canvas2D holds 120 fps at 5,000 branches with no culling, and a batched WebGL2 scene has roughly twenty times that headroom. Real maps will add text layout, hit-testing, editing, SVG textures and re-tessellation, which the spike did not measure. The 50,000-node stress map is within the WebGL2 headroom for drawing but is unmeasured for everything else.

Camera and precision

Zoom towards the cursor by keeping the world point under the cursor fixed. With pan p, cursor c, and zoom changing from z to z', the new pan is p' = c - (c - p) * (z' / z). This is standard mathematics and is the report's own formulation of it; the notes found no source on zoom and pan feel in shipping products, so the feel (inertia, trackpad against wheel) is a gap to explore hands-on.

Proposed design At extreme zoom, 32-bit floats on the GPU lose precision, which shows as jittering geometry. Keep the camera and node positions in double precision (or as offsets relative to a parent or island origin) in the model, and subtract the camera position on the CPU so that the GPU receives small camera-relative floats. The notes mark this as background knowledge, not a sourced result.

Spatial index, level of detail and semantic zoom

Proposed design Use a static R-tree, bounding-volume hierarchy or uniform grid over node and branch bounds, updated incrementally after layout changes, for both culling and hit-testing. tldraw documents an R-tree index and level-of-detail rendering by on-screen size tldraw perf. The spike's culled Canvas2D run drew about 14 per cent of the branches and cut script time from 3.45 to 0.82 ms, which shows the benefit even at small scale.

Semantic zoom means that what is drawn changes with the zoom, not only its size. Proposed design Below a screen-size threshold, replace text by short bars, replace pictures by a low mip level or a dominant colour, and collapse deep subtrees into a single stand-in. The one shipping precedent the notes found is Heptabase: zooming out keeps section titles legible Heptabase sections, which maps to showing a subtree's title or summary when its detail would be unreadable. Heptabase also recommends a higher-level whiteboard above roughly 100 cards and has improved large-whiteboard dragging and rendering Heptabase changelog, which shows that large canvases need this design. Figma and tldraw treat caching of static content into textures or tiles as standard practice, but the notes found no primary source for Figma's tile-based rendering, so it is not claimed here.

Frame budgeting and rendering on demand

The budget is 8.3 ms per frame at 120 Hz and 16.7 ms at 60 Hz, with script time at most 4 ms on a 5,000-node map during pan and zoom. The notes suggest spending under 2 to 3 ms on culling and draw-list building, and keeping decoding and layout off the render thread. The renderer should draw only when something changed (a camera move, an edit, an animation step or a finished asset), so an idle map costs nothing. If a frame is going to be late, the engine lowers the level of detail first, before dropping frames.

Idea for Radiant

Keep the spike scene as a permanent benchmark harness, and extend it with real content: a generated 5,000-node map with 300 pictures, real labels, and hit-testing. The first milestone then measures what the notes could not, and every later engine change can be compared against the same numbers.

ENG-19Must

Zoom towards the cursor

Zooming must keep the world point under the cursor fixed on screen, using the camera relation p' = c - (c - p) * (z' / z).

Accept when: a test zooming from the minimum to the maximum zoom around five cursor positions moves the world point under the cursor by less than one device pixel. Why: basic canvas behaviour; user-facing zoom features are on the features page.

ENG-20Should

Camera-relative precision

The camera and node positions must be held as double-precision values (or local offsets), and the CPU must convert to camera-relative single-precision values before upload, so geometry does not jitter at extreme zoom or far from the origin.

Accept when: at the maximum zoom, panning by one pixel moves every visible vertex by one pixel (no visible shimmer), tested at a node 100,000 world units from the origin. Why: proposed design from general knowledge, not sourced; confirm in the spike.

ENG-21Must

Spatial index for culling and picking

The engine must maintain a spatial index over node and branch bounds, update it incrementally after layout, and use it for culling, hit-testing and marquee selection.

Accept when: on the large reference map, building the visible set for a frame takes under 2 ms of script, and culling draws no more than the items intersecting the viewport plus a margin. Why: script budget of 4 ms per frame; the notes suggest 2 to 3 ms for culling and draw-list work.

ENG-22Should

Level of detail and semantic zoom

The scene layer must choose a drawing level per item from its on-screen size: full detail, labels as bars, pictures as low-resolution or dominant-colour stand-ins, and collapsed subtrees as a single titled stand-in that keeps its title legible.

Accept when: on the 50,000-node stress map at the fully zoomed-out view, frame time stays within 16.7 ms, and every collapsed stand-in at that view still shows its title at a readable size. Why: Heptabase precedent (the only shipping example found); everything else here is proposed design.

ENG-23Must

Render on demand and pace to the display

The engine must draw a frame only when something changed, must measure the actual refresh interval and adapt, and must meet its work budget at both 8.3 ms and 16.7 ms.

Accept when: an idle map issues no draw calls over ten seconds; the mean frame interval on the 120 Hz display with the private flag active is 8.3 ms and falls back to 16.7 ms without errors when the flag is unavailable. Why: decision D-02; the 60 Hz fallback must remain smooth.

ENG-24Should

Permanent benchmark harness on real content

The repository must contain a repeatable benchmark that measures mean, 95th and 99th percentile frame interval and script time per frame on the three reference maps, in the same format as the spike.

Accept when: one command produces a table for the small, large and stress maps at both 60 and 120 Hz, and a regression of more than 10 per cent in mean script time fails continuous integration (the threshold is a proposal). Why: the spike measured a synthetic scene once per configuration; see the quality page.

Picture subtrees can produce hundreds of images. The engine must keep memory bounded and the frame loop free of decoding, which means decoding off the main thread, a thumbnail pyramid, a texture budget with eviction, and placeholders while pictures arrive. Most of this section is the report's recommendation; the notes include a few sourced facts and say explicitly that atlas-against-array choices, AVIF, JPEG XL and LRU budgets were not researched.

SVG at scale

SVG artwork is rendered by the browser engine (decision D-12). Visible SVG subtrees are rasterised into textures per zoom bucket for speed, and shown as live inline SVG only while the user inspects one closely. The main reason is capability: generated SVG can use gradients, clipping and filters that the small native SVG libraries do not support.

Rendering choices

The notes compared the alternatives. resvg supports a static SVG subset, is memory-safe Rust, renders with tiny-skia, has no native text rendering, and uses usvg to produce a simplified tree that another backend can draw resvg. ThorVG targets SVG Tiny, offers CPU, GL, WebGL and WebGPU backends with masking, blending, gradients, blur and drop shadow, in a core of about 170 KB; its performance figures are the project's own ThorVG. Vello is a vector GPU renderer (see the Branches section). These suit a pure native path. For the WebView stack, the browser's own engine supports the full feature set at no extra size, and a later native shell (decision D-17) could use resvg or ThorVG behind the same interface. The notes did not research Skia's SVG module, lunasvg, NanoSVG or librsvg, and measured no re-rasterisation cost; the spike did not test SVG at all.

Zoom buckets and live view

Proposed design Rasterise each visible SVG node group, or the whole subtree, to a texture at a small number of discrete zoom levels (buckets). Drawing uses the bucket nearest the current zoom; when the camera crosses to another bucket, the new texture is rasterised in the background and swapped in, so the previous bucket keeps showing until then. When the user zooms deep into one SVG subtree to inspect it, the engine mounts the sanitised SVG as live inline DOM at that spot and removes it again when the user leaves. Bucket size, cost and the number of live elements that stay smooth are open questions for the SVG spike in milestone M5.

Sanitising untrusted SVG

SVG written by a language model must be treated as untrusted. DOMPurify permits HTML, SVG and MathML by default, supports USE_PROFILES: {svg: true, svgFilters: true} to restrict output to SVG, and strips event handlers such as onload; its README does not state the default handling of foreignObject, and shows a hook to remove it DOMPurify. The report therefore requires an explicit allowlist and explicit removal of risky elements rather than relying on defaults.

Proposed design Allowed elements: svg, g, path, rect, circle, ellipse, line, polyline, polygon, defs, linearGradient, radialGradient, stop, clipPath, mask, title, desc, with transform, fill, stroke and opacity. Forbidden: script, foreignObject, image with an external href, use with an external href, style containing @import, event attributes and animation elements. Filters are costly and unevenly supported, so avoid them or allow only feGaussianBlur and feDropShadow. The node contract of decision D-11 forbids text elements, so the keyword is drawn by the engine. The contract details, repair and fallback behaviour are on the art subtrees page.

The browser-engine route has one additional safeguard to specify: the sanitised SVG is drawn from a document with no network access, so a missed external reference cannot leak anything. The notes do not cover this mechanism, so it is a design requirement to verify rather than a documented behaviour.

ENG-29Must

Allowlist sanitiser for generated SVG

All generated or imported SVG must pass an allowlist sanitiser before it is stored, rasterised or mounted, and the sanitiser must remove scripts, event attributes, foreignObject, external references and animation, and must enforce a maximum element count.

Accept when: a corpus of malicious SVG samples (script, onload, foreignObject, external image and use references, style with @import) produces output with none of them, and rendering the sanitised outputs causes zero network requests. Why: model output is untrusted; DOMPurify's SVG profile is a starting point but defaults for foreignObject are not documented; see the security requirements.

ENG-30Should

Zoom-bucket rasterisation with live inspection

The engine must draw visible SVG subtrees from textures rasterised per zoom bucket in the background, keep the old bucket visible until the new one is ready, and mount live inline SVG only for the subtree under close inspection.

Accept when: crossing a bucket boundary on the large map produces no blank frame and no frame over the 8.3 ms budget at 120 Hz, and at most one live SVG subtree is mounted at a time. Why: decision D-12; rasterisation cost is unmeasured, so the accept thresholds depend on the milestone M5 spike.

Data model and undo

The document is a tree of nodes with stable ids, plus separate collections for cross-links, styles and assets. Every edit is an operation with an inverse, recorded in a log that drives undo and redo, autosave and crash recovery, and that would later map onto a collaboration layer.

The model

Node
Stable id (UUIDv7 or ULID), parent, order among siblings (a fractional index), text, note, collapsed flag, representation (vector, raster or SVG), asset reference, style reference and layout fields: an optional manual offset, side and seed. Proposed design
Multiple roots
A document may have several roots, each with its own layout.
Floating node
A node with no parent and an absolute position, for notes that belong to no branch.
Cross-link
An edge between any two nodes, with label and style, stored separately from the tree so the tree stays a tree.
Representation
A per-subtree setting that picks vector, picture or SVG drawing. Every node keeps its text in all three, so search, outline, export and accessibility always work, and switching back is a flag change (decision D-09).
Styles and themes
Named style records referenced by nodes, inheriting from the map's theme; per-subtree style sheets for generated art are described on art subtrees.
Assets
Cached, regenerable images and SVG referenced by hash, with generation metadata (prompt, model, seed, style snapshot), keyed so a text edit invalidates only that node's asset.

Undo and redo

A command log, where each operation carries its inverse, is the simplest approach for a single-user app and maps well onto an operation-log CRDT later; this is the notes' inference. SQLite triggers can also maintain an undo and redo stack inside the database so that undo survives restarts, according to sqlite.org's file-format page SQLite appfileformat. The report recommends application-level operations, not triggers, because group operations such as a multi-node paste or a streamed AI generation must undo as one step. AI generation applies lines as they arrive (decision D-08), so one generation job must be one undo group, however many nodes it adds.

Autosave and crash safety

Each committed operation is written in a SQLite transaction in the host. SQLite's transactional atomic writes, incremental updates and crash-safe continuous saves are listed on the same page, so no separate save step is needed; the operation log doubles as the recovery record.

Looking ahead to collaboration

The notes cover one candidate. Loro provides a movable tree CRDT based on Kleppmann et al., "A highly-available move operation for replicated trees": each node has a unique tree id and an associated map container, sibling order uses a fractional index, and cycles are prevented after concurrent moves merge; its API has create, mov and mov_to Loro tree Loro blog. Automerge and Yjs were not researched, so no comparison is offered. Version 1 needs only a few habits to keep the option open: stable ids for every entity, fractional sibling order, operations that name ids and never positions in a list, and no derived data (layout) stored as truth. Decision D-15 puts a collaboration server, if ever built, on the Elixir side.

ENG-31Must

Stable ids and tree structure

Every node, edge, style and asset must have a stable identifier that never changes or is reused; siblings must be ordered by a fractional index so an insert changes one record; and the model must support multiple roots, floating nodes and cross-links.

Accept when: inserting between two siblings in a 1,000-child list writes exactly one node record, and a test document with two roots, a floating node and a cross-link survives save and reload unchanged. Why: operation log, import and collaboration readiness; Loro uses the same two ideas.

ENG-32Must

Representation as a subtree flag; text always kept

The representation of a subtree (vector, raster or SVG) must be a per-node field and every node must keep its text in every representation. Switching representation must not delete any asset or text and must be reversible with one operation.

Accept when: switching a 50-node subtree from vector to raster to SVG and back, then comparing the exported Markdown outline, gives an identical outline, and undo restores the previous representation. Why: decision D-09.

ENG-33Must

Operation log with grouped undo and redo

Every document change must be recorded as an operation with an inverse, in a log that supports undo, redo and grouped steps, and a whole AI generation job or multi-node paste must undo as one step.

Accept when: applying 1,000 random operations and undoing them all returns a document byte-identical (by content hash) to the start, and redoing all returns the final state. Why: decisions D-08, D-14.

ENG-34Must

Continuous autosave and crash recovery

Each committed operation must reach disk in a transaction so that a crash or forced quit loses at most the operation in progress, and reopening the file must restore the last committed state without a recovery dialog.

Accept when: killing the process 100 times at random points during a scripted edit session leaves a file that opens every time, with at most one operation missing. Why: SQLite's transactional, crash-safe writes; reliability targets are on the quality page.

ENG-35Later

Collaboration-ready operations

Operations must name entities by id and sibling position by fractional index, and must not store derived layout, so a replicated-tree layer (for example Loro's movable tree) could replace the log without changing the model.

Accept when: a review of the operation types finds none that refer to a list index or a stored computed position. Why: keeps the collaboration option open at no cost; the notes did not research Automerge or Yjs.

File format

A map is one SQLite database file (decision D-14). The sqlite.org page on application file formats lists the reasons that fit this app: a single-file document with an application id; transactional, atomic writes; incremental updates that write only changed pages; crash-safe continuous saves; an extensible schema; fast access to just the data needed; blobs under about 100 KB that can be faster than separate files; concurrent readers; cross-platform portability; and backward compatibility since 2004 SQLite appfileformat. The same page warns that users can be tricked into opening a malicious database, so an opened file must be validated, not trusted. The notes add one concern of their own: SQLite files are opaque to diff and sync tools, so a periodic export to a plain bundle should exist for version control.

Schema sketch

Proposed design The tables below are a sketch for discussion, not a final schema; the notes name the tables (nodes, edges, styles, assets, meta, ops) and the asset columns.

-- application_id and user_version set with PRAGMA, so the file is recognisable and versioned
CREATE TABLE meta   (key TEXT PRIMARY KEY, value TEXT);        -- schema version, document seed, theme

CREATE TABLE nodes  (
  id TEXT PRIMARY KEY,            -- UUIDv7 or ULID, stable
  parent_id TEXT,                 -- NULL for a root or a floating node
  sort_key TEXT,                  -- fractional index among siblings
  text TEXT NOT NULL, note TEXT,
  collapsed INTEGER NOT NULL DEFAULT 0,
  representation TEXT NOT NULL DEFAULT 'vector',   -- vector | raster | svg
  asset_hash TEXT,                -- references assets.hash
  style_id TEXT,
  layout_json TEXT,               -- variant, side, manual offset, seed
  x REAL, y REAL                  -- only for floating nodes
);

CREATE TABLE edges  (id TEXT PRIMARY KEY, from_id TEXT, to_id TEXT, label TEXT, style_id TEXT);
CREATE TABLE styles (id TEXT PRIMARY KEY, kind TEXT, json TEXT);

CREATE TABLE assets (
  hash TEXT PRIMARY KEY,          -- content hash: identical bytes are stored once
  mime TEXT, bytes BLOB, width INTEGER, height INTEGER,
  thumbhash BLOB,
  gen_json TEXT                   -- prompt, model, seed, style-sheet snapshot, parent asset
);

CREATE TABLE ops    (seq INTEGER PRIMARY KEY, ts INTEGER, group_id TEXT, op_json TEXT, inverse_json TEXT);

Assets are content-addressed: the primary key is a hash of the bytes, so identical images are stored once and a node refers to an asset by hash. The gen_json column records the prompt, model and style snapshot of each generated asset, which decision D-19 requires and which allows regeneration. Sanitised SVG is stored as text with the validated contract recorded. Layout results are not stored as truth; the notes recommend storing cached positions only as a cache. The host owns the file (decision D-06), so the front end never opens SQLite directly.

Exporting a mixed picture and SVG map

Proposed design A whole-map SVG export inlines each SVG node's sanitised group directly, embeds raster nodes as <image href="data:..."> elements with clip paths where needed, and draws branches and labels as paths and text from the engine's own geometry. Limits of this research

The engine's architecture, layout and rendering rest on a small number of verified sources and one set of measurements. The following points should be read as design, not as established practice.

  • Proposed designs without prior art: organic Buzan-style layout; two-sided balancing by subtree extent; the radial mapping with ring radii for wide pictures; the branch outline pipeline and join rule; per-glyph text along branches with its curvature, direction and script rules; camera-relative precision; zoom-bucket rasterisation with live inline SVG; GPU texture budgets; operation-log undo grouping for AI jobs; the schema sketch; and mixed SVG or PDF export.
  • Sources not fetched or not read in full: Walker (1990) and Buchheim et al. (2002); yFiles, dagre and the internals of Xmind and MindNode layout; Levien's blog posts and kurbo (so the kurbo variable-width limitation is not verified); Skia and Inkscape power stroke; Excalidraw, Miro, Zed, Google Maps and Flutter Impeller engineering write-ups; SVG textPath; HarfBuzz; AVIF and JPEG XL; atlases against texture arrays; Automerge and Yjs; the OPML, FreeMind and Mermaid mindmap specifications; PDF export tooling.
  • Weakly sourced: Figma's tile-based rendering (only a secondary tutorial claims it); the patent expiry date quoted by a blog commenter; the Xmind file structure (community tools and an encyclopaedia, no official schema); ThorVG's benchmark claims (the project's own); Safari and WKWebView behaviour on other OS builds, where a Tauri plugin README contradicts the measurement on macOS 26.5.1 plugin README.
  • Not measured: Electron or Chromium, input latency, SVG rendering and re-rasterisation, real text layout, hit-testing, editing, memory, thermal behaviour, older Apple Silicon and Intel Macs, the 400,000-branch row against a single process (the 10,000 to 50,000 and the 100,000 to 400,000 rows come from different runs), and any display that is not the built-in 120 Hz panel.
