Functional requirements

This page lists 142 numbered functional requirements for everything the user does in Radiant other than AI generation and picture or SVG artwork. Each requirement is specific enough to implement and test, carries a priority, and links to the research page that justifies it. 44 of them are Must, the minimum for a usable first version.

Read this page together with the vision and scope page, which explains the principles behind the choices, and with the other requirement pages: AI generation and the Codex engine (prefix FR-AI), picture and SVG subtrees (FR-ART), engine internals (ENG) and non-functional requirements (NFR). The end of this page has a traceability table that shows which requirement answers each MindNode feature and each ranked community need.

How to read this page. Each requirement has an identifier that never changes, a priority, a short statement, an acceptance check and the reason. Must means needed for the first usable version (milestones M1 to M3). Should means part of version 1 (up to milestone M6). Could means worth doing after version 1 if it proves valuable. Later means deliberately deferred. A requirement that says "must" in its text is binding once its priority is reached. Wherever the evidence page and Tony Buzan disagree, the behaviour is a default that the user can change, and the requirement says so. Numbers in acceptance checks come from the performance targets that this report proposes, which the spikes in milestone M0 are to confirm. The milestone given for each requirement is the earliest milestone of the roadmap in which it should be built.

Canvas and navigation

The canvas is where the user spends most of the time, so its conventions follow the trackpad habits of other canvas tools and keep a very large map navigable. Speed targets for pan and zoom are non-functional requirements and sit on the quality page.

FR-CAN-01Must

Infinite canvas

The canvas must have no fixed page or bounds. The user must be able to pan in any direction without limit, and content must never be clipped to a page edge.

Accept when: Drag a node repeatedly in one direction and keep panning after it. Text and branches stay sharp and do not jitter at any distance reached. Why: The infinite canvas is one of the stated goals and MindNode adopts it (MindNode verdicts). Milestone: M1.

FR-CAN-02Must

Trackpad and mouse conventions

Two-finger scroll must pan, pinch must zoom, and a mouse wheel with the Command key held must zoom. Holding Space and dragging, or dragging with the middle button, must pan.

Accept when: On a trackpad the four gestures work as described. On a mouse with a wheel, Command plus wheel zooms and plain wheel pans. Each convention can be changed in settings. Why: These are the controls familiar from other canvas tools such as Kinopio and Heptabase (AI and canvas tools). Milestone: M1.

FR-CAN-03Must

Zoom towards the cursor

Zooming must keep the point under the cursor (or the pinch centre) fixed on screen, so the user zooms into what they are looking at.

Accept when: Place the pointer over a node, zoom in and out by wheel and by pinch. The node stays under the pointer throughout. Why: A zoom that drifts away from the pointer makes a large map hard to navigate; this is the standard canvas behaviour in the desktop tools. Milestone: M1.

FR-CAN-04Must

Zoom commands and zoom to fit

Radiant must offer zoom in (Cmd++), zoom out (Cmd+-), reset to 100% (Cmd+0) and zoom to fit the whole map (Cmd+*), all from the menu and the keyboard.

Accept when: After zoom to fit, every node of the document is inside the window with a margin. Reset to 100% returns the scale to exactly 100%. Why: These are MindNode's documented zoom shortcuts, adopted as they are (MindNode shortcuts). Milestone: M1.

FR-CAN-05Must

Zoom to selection and centre selection

Radiant must zoom to fit the current selection and must centre the selection without changing the zoom (Shift+Cmd+8).

Accept when: Select a deep branch and run the command. All selected nodes fill the window. The centre command changes the position only. Why: MindNode provides both commands and users depend on them to find their place in large maps (MindNode). Milestone: M1.

FR-CAN-06Should

Focus on a branch

Radiant should offer a focus mode (Shift+Cmd+F) that dims or hides everything outside the selected branch and zooms to it. Escape must leave the mode and restore the previous view.

Accept when: Enable focus on a branch: nodes outside it are not drawn at full strength, and Escape returns to the earlier zoom and position. No node is moved or edited by entering or leaving the mode. Why: MindNode lists Focus Mode but does not document it, so the behaviour is specified from scratch here (MindNode verdicts, status unverified). Milestone: M1.

FR-CAN-07Should

Minimap

Radiant should show an optional minimap with the viewport rectangle, in which clicking or dragging moves the view.

Accept when: Toggle the minimap from the View menu. Dragging the viewport rectangle pans the main canvas, and the minimap tracks every pan and zoom. Why: Orientation aids such as minimaps help in large hierarchies (evidence, moderate) and users report that big maps are hard to navigate (community). Milestone: M3.

FR-CAN-08Must

Several main nodes on one canvas

A document must be able to hold any number of main nodes, each with its own tree, on one canvas. A command must create a new main node at the view centre (Shift+Return in the MindNode keymap preset, see FR-EDT-23).

Accept when: Create three main nodes in one document, give each its own children, and save and reopen. All three trees return as they were. Why: MindNode supports several main nodes and the reader uses this today (MindNode verdicts, Adopt). Milestone: M1.

FR-CAN-09Should

Floating nodes

The user must be able to place a free text or image node that belongs to no tree, to hold annotations and loose ideas beside the map. Floating nodes must survive re-layout and appear in search and export.

Accept when: Create a floating label, run a layout on the map beside it, and confirm the label has not moved. Search finds its text. Why: Coggle and Scapple support free labels and images outside the tree (desktop tools). Milestone: M3.

FR-CAN-10Must

Level of detail the user can see

As the user zooms out, the app must keep the structure readable: labels that would be too small to read must give way to a simplified form, and a collapsed subtree must show its title. Nothing may turn blank, and full detail must return as the user zooms in.

Accept when: Zoom a large reference map out to the whole-map view and back. At every step each branch is still visible as a shape and every visible label is legible or replaced by a title. The frame budget in the quality requirements still holds. Why: Heptabase shows section titles when zoomed out (desktop tools) and the geometry stays constant across levels of detail (engine). Milestone: M1.

FR-CAN-11Must

Single and multiple selection

Clicking a node must select it. Shift-click or Command-click must add or remove nodes from the selection, and the selection must be visible at every zoom level.

Accept when: Select two unrelated nodes with Command-click, then deselect one. Delete, move and style commands apply to exactly the selected set. Why: Basic selection is needed for every editing command (MindNode). Milestone: M1.

FR-CAN-12Must

Marquee selection

Dragging on empty canvas must draw a rectangle that selects every node it touches. Holding Shift must add to the existing selection.

Accept when: Drag a rectangle across five nodes and all five are selected. Holding Shift while dragging keeps the earlier selection. Why: Marquee selection is the usual way to move or style many nodes at once on a canvas tool. Milestone: M1.

FR-CAN-13Could

Subtree and sibling selection

Radiant should provide commands to select the current node with all its descendants, all siblings of the current node, and all nodes at the same level, plus Shift+arrow to extend the selection in a direction.

Accept when: Select a node, run Select subtree, and every descendant (and nothing else) is selected. Copying then copies the whole subtree. Why: MindNode offers "select next in a direction" with Shift+arrow (MindNode shortcuts); subtree selection supports subtree representation changes in art subtrees. Milestone: after version 1.

FR-CAN-14Should

Smooth animated transitions

Fold, unfold, re-layout, zoom to fit and pan-to-node must animate over a short, fixed time so the user can follow what moved. The animation must be skipped when the system setting Reduce Motion is on.

Accept when: Fold a branch and the siblings below glide into place. With Reduce Motion enabled the same action completes with no intermediate frames. Why: Brief animation preserves the user's mental map (evidence, moderate; practice). Milestone: M1.

FR-CAN-15Should

Selection stays in view

When the selection changes by keyboard (arrows, new node, undo), the app must scroll the canvas just enough to keep the selected node inside the window without changing the zoom.

Accept when: Press the arrow key repeatedly towards the screen edge. The selected node never leaves the window. Why: Keyboard-first use needs the view to follow the cursor of the keyboard (community, rank 2). Milestone: M1.

FR-CAN-16Could

Presentation mode

Radiant could walk through chosen branches in order, zooming to each, with a full-screen view that hides panels.

Accept when: Pick three branches, start the walk-through, and each Space press moves to the next branch with a zoom transition. Why: Xmind turns a map into slides and has a full-screen mode (desktop tools); lower priority than the core. Milestone: after version 1.

Editing and keyboard

Radiant copies the keyboard model that MindNode and most other mappers share, so a user moving from MindNode keeps their habits. The few places where tools disagree are configurable.

FR-EDT-01Must

Create a child node

Tab must create a child of the selected node, place it in edit mode and select it. The command must also exist in the menu.

Accept when: Select a node, press Tab, type text and press Escape. A new child with that text exists under the selected node. Why: Tab for child is the de facto convention across MindNode, Xmind, SimpleMind and Whimsical (desktop tools). Milestone: M1.

FR-EDT-02Must

Create a sibling after

Return must create a sibling after the selected node and begin editing it. On a main node it must create a new main node, never a sibling.

Accept when: Select a child, press Return, type and press Return again. Two new siblings follow in order. Why: Return or Enter for a sibling is the cross-tool standard (desktop tools). Milestone: M1.

FR-EDT-03Must

Create a sibling before

Shift+Return must create a sibling before the selected node. Option+Return must do the same, as an alias for MindNode users.

Accept when: Select the second child and press Shift+Return. The new node is placed between the first and second child. Why: Shift+Return is the shared convention of Xmind, MindMup and Freeplane (desktop tools). MindNode uses Option+Return, so both are bound. Milestone: M1.

FR-EDT-04Should

Insert a parent

Option+Tab should insert a new node between the selected node and its parent, so that the selected node becomes its child. This key is configurable.

Accept when: Select a child and press Option+Tab. A new node appears between it and its former parent and enters edit mode. Why: MindNode binds Option+Tab; the other tools have no standard (MindNode, desktop tools). Milestone: M1.

FR-EDT-05Must

Navigate with arrow keys

Arrow keys must move the selection to the nearest node in that direction, and must follow the branch structure (left or right to parent or child on a horizontal layout).

Accept when: From any node, the four arrows reach its parent, first child and neighbouring siblings on a two-sided map without using the mouse. Why: Arrows are the universal navigation key (desktop tools). Milestone: M1.

FR-EDT-06Must

Inline editing

F2 and Command+Return must start editing the selected node, as must typing a printable character, which replaces the text. While editing, Return must commit the text and create the next sibling, Escape must commit and stop, and Shift+Return must insert a line break in the label. Text input must work with input methods.

Accept when: Edit a node with each key. Enter Japanese text using the system input method and the committed text appears correctly. Why: F2 and Space or Return are the two competing edit conventions (desktop tools); ordinary HTML text editing gives input-method support (stack decision). Milestone: M1.

FR-EDT-07Must

Rapid entry of many nodes

A new node created with Tab or Return must already be in edit mode, so a user can type an entire tree by keyboard alone. Typing, Tab and Return must never drop characters while the layout animates.

Accept when: Type a 20-node tree using only Tab, Return and letters. The result has the expected shape and no lost characters. Why: Keyboard-first flow is rank 2 among the ranked needs on the community page. Milestone: M1.

FR-EDT-08Must

Delete a node

Delete must remove the selected node and its subtree. Option+Delete must remove only the node and promote its children to its parent. A confirmation must be needed only when the deletion cannot be undone.

Accept when: Delete a branch of five nodes, then undo. All five return in place. Option+Delete on a node with three children leaves the three under its parent. Why: These are the MindNode and cross-tool defaults (MindNode shortcuts). Milestone: M1.

FR-EDT-09Must

Undo and redo of everything

Cmd+Z and Shift+Cmd+Z must undo and redo every change to the document: text, structure, moves, folds, styles, representation switches, imports and AI changes. An AI generation must undo as a single step, and the undo stack must hold unlimited steps within a session.

Accept when: Make ten different kinds of edit, including a generation, and undo them all in order. The document equals its starting state. Why: Reliable undo is expected of any editor, and a revertible AI step supports the draft-then-rework approach (evidence; AI engine). Milestone: M1.

FR-EDT-10Could

Undo survives restart

The undo history should be kept in the operation log so that closing and reopening a document does not discard it.

Accept when: Edit, quit, reopen, and undo. The last edit is reverted. Why: The file format keeps an operation log for undo and crash safety (decision D-14; engine). Milestone: after version 1.

FR-EDT-11Must

Drag to re-parent

Dragging a node onto another node must make it that node's child, with its subtree. A visible drop target must show where it will land, and dropping a node onto its own descendant must be impossible.

Accept when: Drag a branch onto another node and it becomes the last child. Dragging onto its own child is refused with no change. Why: Drag-and-drop restructuring is basic to mapping tools (MindNode). Milestone: M1.

FR-EDT-12Must

Reorder siblings

Command+Up and Command+Down (and Command+Left and Right on a vertical layout) must move the selected node among its siblings, and dragging between two siblings must insert there.

Accept when: Press Cmd+Up on the third child. It becomes second and the other siblings keep their relative order. Why: Cmd or Ctrl plus arrows is the cross-tool convention (desktop tools). Milestone: M1.

FR-EDT-13Should

Detach and reattach

Shift+Cmd+D must detach the selected node into a new main node, keeping its subtree. Dragging a main node onto another node must attach it as a child. Holding the D key while dragging must detach during a drag.

Accept when: Detach a child, check it is a main node with its subtree, then drag it back onto its old parent. The structure matches the original. Why: MindNode documents both gestures (MindNode). Milestone: M1.

FR-EDT-14Must

Fold and unfold

Option+period must fold or unfold the selected node. A folded node must show an indicator with the number of hidden descendants. Folding must work on every representation of a subtree.

Accept when: Fold a branch. The indicator shows the right count and hidden nodes are neither drawn nor selectable. Search still finds them. Why: Collapse is a core interaction (community) and a requirement for picture and SVG subtrees to stay collapsible (art subtrees). Milestone: M1.

FR-EDT-15Should

Fold with siblings and unfold one level

Radiant should offer fold with siblings, unfold one level, fold all to level n, and unfold all, from the menu and keys (Option+Cmd+period for fold with siblings, Ctrl+Option+period for unfold one level).

Accept when: Run unfold one level on a folded root. Exactly its next level appears and no deeper node. Why: MindNode documents these actions (MindNode, Adopt). Milestone: M1.

FR-EDT-16Must

Cut, copy, paste and duplicate subtrees

Cut, copy and paste must work on a selection of nodes with their subtrees, preserving styles, notes, links and images. Cmd+D must duplicate the selection beside the original. Paste must place the copy as a child of the selected node.

Accept when: Copy a styled branch with an image and paste it under another node. Text, style, note and image are identical, and the original is unchanged. Why: Standard editing behaviour (MindNode shortcuts). Milestone: M1.

FR-EDT-17Should

Paste between documents and as text

Copied subtrees must paste between open documents with their styles and assets, and the clipboard must also carry an indented plain-text outline so that pasting into a text editor produces a readable list.

Accept when: Copy a branch in one document and paste in another. Assets arrive. Paste into a text editor and an indented list appears. Why: Moving material between maps is the basis of splitting large subjects (community). Milestone: M3.

FR-EDT-18Should

Paste an outline to make a subtree

Pasting indented text, a Markdown list or OPML text onto a node must create a subtree whose shape follows the indentation, as one undo step.

Accept when: Paste a ten-line indented list onto a node. Ten nodes appear with the indentation as structure. One undo removes them all. Why: The top Hacker News mind-map story was "Convert Markdown to a Mind Map" (community), and the outline is the interchange form with the AI (MindNode). Milestone: M3.

FR-EDT-19Should

Multi-line notes

Each node should hold a multi-line note in plain text or Markdown, opened with Shift+Cmd+K in a notes panel. A node with a note must show a small indicator.

Accept when: Add a three-line note, close the panel, and see the indicator. The note is saved, searchable and exported. Why: MindNode has notes with a sidebar (MindNode verdicts, Adapt: start with plain text or Markdown). Milestone: M3.

FR-EDT-20Should

Links on nodes

Cmd+K must attach a web link or file link to a node, shown with an indicator. Cmd-clicking the indicator must open it.

Accept when: Attach a URL to a node and open it with Cmd-click in the default browser. Why: Cmd+K for link is the MindNode default (MindNode shortcuts). Milestone: M3.

FR-EDT-21Should

Paste or drop an image onto a node

Pasting or dropping an image file on a node must attach it to the node as a resizable picture, stored as an asset. Dropping on empty canvas must create a floating image node.

Accept when: Drop a PNG onto a node. It appears at a sensible size, can be resized with handles, and is saved in the document. Why: MindNode attaches stickers and photos with resize knobs (MindNode verdicts, Adapt). The picture representation of a whole subtree is covered on art subtrees. Milestone: M3.

FR-EDT-22Could

Command palette

Shift+Cmd+P must open a searchable list of every command with its shortcut. Choosing a command must run it.

Accept when: Open the palette, type "fold" and run Fold. Every menu command is reachable here. Why: A command palette makes a large keyboard model discoverable and supports the keyboard-first goal (community). Milestone: after version 1.

FR-EDT-23Should

Configurable shortcuts and presets

Every shortcut must be remappable, with conflict detection. A "MindNode" keymap preset must be offered in which Shift+Return creates a new main node and Option+Return a sibling above.

Accept when: Remap fold to another key, see a conflict warning when reusing a bound key, and switch to the MindNode preset. Why: No standard exists for parent, fold, note and link, so they must be configurable (desktop tools). Milestone: M3.

FR-EDT-24Must

Commands on a multiple selection

Delete, move, fold, style, tag and representation commands must apply to every node in a multiple selection in one undo step.

Accept when: Select four siblings, apply a colour, and one undo reverts all four. Why: Multiple selection is only useful if commands honour it. Milestone: M1.

FR-EDT-25Could

Sort children

Radiant could sort the children of a node alphabetically or by task state from a menu command.

Accept when: Sort three children alphabetically. They are reordered and one undo restores the old order. Why: MindNode has this as a menu command (MindNode). Milestone: after version 1.

FR-EDT-26Could

Emoji and symbols

Radiant could insert an emoji or symbol into a label or beside a node from a picker.

Accept when: Insert an emoji from the picker and it renders in the label and in exports. Why: MindNode supports emojis and stickers (MindNode). Milestone: after version 1.

FR-EDT-27Later

LaTeX equations in notes

Radiant could render LaTeX equations in notes, after notes are done.

Accept when: Deferred. Accept when a note containing an equation shows the typeset result. Why: MindNode added LaTeX in July 2026; the verdict is to adapt it in a later phase (MindNode verdicts). Milestone: after version 1.

FR-EDT-28Later

Menu-bar quick capture

Radiant could provide a menu-bar capture window that adds a node to a chosen document.

Accept when: Deferred. Accept when text typed into the capture window lands in the chosen map without opening it. Why: The behaviour of MindNode's Quick Entry is unverified, so it would be specified from scratch (MindNode verdicts). Milestone: after version 1.

FR-EDT-29Later

Pen and sketch input

Radiant could let the user draw on or beside a node with a pen or finger and keep the strokes editable.

Accept when: Deferred. Accept when a stroke drawn on a node survives save, reopen and export. Why: Sketching helps memory (evidence, moderate to strong) and the ink-plus-structure combination is an open gap (community, rank 10), though the evidence is weak. Milestone: after version 1.

Layout

Layout is automatic but never surprising. The core rule is that the app does not move anything the user has already seen, unless asked. How the layout algorithm works is described on the engine page.

FR-LAY-01Must

Automatic layout without overlap

New and edited nodes must be placed by an automatic layout that handles nodes of different sizes and never lets two nodes overlap.

Accept when: Add 50 nodes of varied label length. No node box intersects another. Why: Automatic layout is the baseline expectation (MindNode); the algorithm is chosen in engine. Milestone: M1.

FR-LAY-02Must

Unrelated branches never move

An edit inside one branch must not change the position of any node outside its main branch, and the node being edited must keep its position on screen.

Accept when: Add, delete and fold nodes in one main branch and compare every position in the others before and after. All are identical. Why: Layout instability is the most repeated layout complaint (community, rank 1); stable positions are moderately supported (evidence). Milestone: M1.

FR-LAY-03Must

Never re-lay out a map the user has seen

Opening a document must reproduce the stored positions exactly. The app must re-run layout on existing nodes only when the user asks or when a local edit requires room.

Accept when: Open a saved map three times. Positions are identical each time and no layout runs over untouched branches. Why: Same rank-1 need as above; positions are stored so that maps stay recognisable (practice). Milestone: M1.

FR-LAY-04Must

Manual moves stored as offsets

Dragging a node must store an offset from its automatic position, so that the node and its subtree follow when the parent moves.

Accept when: Drag a child away, then move its parent. The child moves with the parent and keeps the same relative offset. Why: This is how MindNode behaves and the engine page specifies the storage (MindNode; engine). Milestone: M1.

FR-LAY-05Should

Snap-back preview and reset position

While dragging, a shadow must show the automatic position. Ctrl+Cmd+R must clear the offset of the selected nodes, and a menu command must clear all offsets in a subtree or document.

Accept when: Drag a node, see the shadow, release, then reset. The node returns to the shadow position. Why: MindNode shows this shadow and has Reset Position (MindNode). Milestone: M1.

FR-LAY-06Must

Two-sided and one-sided layouts

Each main node must have a layout choice of two-sided horizontal and one-sided horizontal, stored per main node.

Accept when: Set one main node to two-sided and another to right only, in the same document. Both persist after reopening. Why: MindNode sets layout per main node (MindNode, Adapt). Milestone: M1.

FR-LAY-07Should

Radial, vertical, compact and outline-like layouts

Each main node should also offer radial, top-down, bottom-up, compact (organisation chart) and outline-like variants.

Accept when: Switch a main node through every variant. No variant produces overlaps and each is undoable. Why: MindNode offers horizontal, vertical, compact and radial; the decision brief adds outline-like (MindNode, decision D-13). Milestone: M3.

FR-LAY-08Could

Layout variant per subtree

Radiant could let any subtree use a different layout variant from its parent, so that a picture or SVG subtree can use the layout that suits its art.

Accept when: Set one branch to radial inside a horizontal map. Its parent connects to it cleanly and the rest is undisturbed. Why: MindNode applies layout per main node and the verdict is to extend it per subtree (MindNode verdicts, Adapt). Milestone: after version 1.

FR-LAY-09Should

Organic layout

An organic layout option should apply a seeded geometric variation on top of the automatic layout. The seed must be stored in the document so that a file always draws the same picture.

Accept when: Open the same file on two machines. The picture is pixel-identical at the same zoom. A "new variation" command changes the seed and is undoable. Why: Organic look is a core differentiator and the seed keeps layout reproducible (decision D-13; engine). No published algorithm exists, so the design is proposed. Milestone: M3.

FR-LAY-10Should

Balance a main node

A Balance command (Option+Cmd+B) should rebalance children between the two sides of a main node by subtree size. It must run only when asked and must not change the sides of unrelated branches otherwise.

Accept when: On a lopsided map, Balance evens both sides. Without running it, adding a node never flips an existing branch to the other side. Why: MindNode has Balance in its Organize menu (MindNode). Milestone: M3.

FR-LAY-11Should

Spacing control

Spacing must be selectable as narrow, default or wide per main node, and the setting must be stored with it.

Accept when: Switch spacing to wide on one main node. Distances between its nodes grow and the other main nodes are untouched. Why: MindNode has narrow, default and wide spacing, and spacing is part of design in Buzan's Law 10 (MindNode; Buzan). Milestone: M3.

FR-LAY-12Should

Re-layout on demand

A Tidy command should re-run automatic layout for the selection or whole document, animated and undoable, with a warning that manual offsets will be cleared if the user chooses that option.

Accept when: Run Tidy on a map with manual offsets and choose to keep them. Offsets are kept and overlaps are resolved. Undo restores the earlier picture. Why: The user needs an explicit control since layout never changes by itself (community). Milestone: M3.

FR-LAY-13Must

Layout on fold and unfold

Folding or unfolding a node must move only the nodes that need to give or take room in the same main branch, with the node under the pointer staying still, and the change must animate.

Accept when: Unfold a node in the middle of a map. The node does not jump on screen, other main branches do not move, and later siblings make room. Why: Same stability rule as FR-LAY-02, applied to the most frequent edit (engine). Milestone: M1.

FR-LAY-14Could

Pin a node

Radiant could let a node be pinned at an absolute position that ignores its parent's movement.

Accept when: Pin a node, move its parent, and the pinned node stays where it was. Why: Practice sources recommend a pin option beside stable layout (practice). Milestone: after version 1.

FR-LAY-15Later

Layouts beyond trees

Radiant could add timeline or path, columns, grid and popcorn layouts for sequential or categorised material.

Accept when: Deferred. Accept when a main node can be switched to a timeline and keeps its content. Why: Weak support from a secondary guide (practice). Milestone: after version 1.

Styles and themes

Looks are views of the tree. This area covers theme, branch and node style, Tony Buzan's laws as an optional preset with its own switches, and the tools for emphasis. Picture and SVG representations of a subtree are covered on art subtrees.

FR-STY-01Must

Document theme

A document must have one theme that defines canvas colour, main node style, child node style, branch style, branch colouring, connection style and fonts. Changing the theme must restyle the whole document in one undo step.

Accept when: Switch theme on a styled map. Every node, branch and connection takes the new look and one undo restores the old look. Why: MindNode themes cover exactly these properties (MindNode, Adopt). Milestone: M1.

FR-STY-02Must

One colour per main branch

Each main branch must receive its own colour from the theme palette, inherited by all its descendants and its branches, and the user must be able to override it for a branch or a node.

Accept when: Create five main branches. Each gets a different colour and its descendants share it. Overriding one subtree changes only that subtree. Why: Colour as a code is strongly supported for cueing (evidence) and is Buzan's Law 8 (Buzan). Milestone: M1.

FR-STY-03Must

Text formatting

The user must be able to set font family, size, bold, italic, colour and alignment on selected nodes. Default sizes must fall with depth. Default fonts must be plain and readable at the default zoom.

Accept when: Select three nodes and apply bold and a size. Only those nodes change, and the defaults for new nodes are unchanged. Why: Size variation expresses hierarchy (Buzan); deliberately hard-to-read fonts do not aid memory (evidence, strong against). Milestone: M1.

FR-STY-04Must

Branch shapes

Branches must be available as rounded, angular and tapered organic curves, selectable per document and per main branch, so that more than one style can appear in one map.

Accept when: Set one main branch to angular and another to tapered. Both render and persist. Why: MindNode has rounded, angular and (since July 2026) tapered branches, and reviewers asked for both in one map (MindNode). Milestone: M1.

FR-STY-05Should

Tapered organic branches at every level

Organic branches must be drawn as one filled outline with the width falling from thick at the centre to thin at the tip, at every level of the tree. A child branch must start inside the parent branch outline with no visible seam, and the user must be able to thicken an outer branch.

Accept when: Zoom to maximum on a joint between a parent and a child branch. No gap or step is visible. Thicken an outer branch and its width increases without affecting siblings. Why: Buzan's Law 6 and 7 (Buzan); MindNode tapers only first-level branches (MindNode verdicts, Adapt). Curves carry a preference benefit but no memory benefit in the evidence (science). Milestone: M3.

FR-STY-06Should

Text on or beside the branch

The theme must offer a mode in which a node's label sits on its branch, with the branch drawn as an underline whose length equals the label length, and a mode in which the label sits in a node shape. Labels must stay horizontal.

Accept when: Switch a map between the two modes. In the first, no box surrounds a label and each branch ends where its label ends. Labels are never rotated. FR-STY-10Should

Buzan preset

The Buzan strict preset must apply his laws as defaults: blank canvas with no grid or lines, a landscape export frame, uppercase keyword text, one colour per main branch, curved tapered branches, branch length equal to label length, a central image of at least three colours, upright text, and no boxed phrases, optional colour or multiple centres.

Accept when: Apply the preset to a new map. Each default listed is visible in settings as an individual switch that is on. Why: Buzan's rules 1 to 16 and 23 (Buzan). Software that allows boxed phrases and optional colour produces concept maps, he says (history). Milestone: M3.

Outline panel

The app must show the map as an outline in a panel beside the canvas, toggled with Cmd+2 (map only with Cmd+1), with main nodes in creation order and children in map order.

Accept when: Open the panel on a map. Every visible node appears once, indented by depth, in the stated order. Milestone: M3.

FR-OUT-02Must

Two-way synchronisation

A change in the outline must appear on the canvas, and the reverse, within the same frame. Selection and fold state must follow in both directions, and scrolling the outline must keep the selected node visible.

Accept when: Type in the outline and watch the label change on the map. Select a node on the map and it highlights in the outline. Why: Live two-way sync is what makes the outline useful (MindNode). Milestone: M3.

FR-OUT-03Should

Outline keyboard editing

In the outline, Tab must indent, Shift+Tab must outdent, Return must split a node at the cursor, and Backspace at the start of a node must merge it with the previous one. Cmd+Up and Down must move the node.

Accept when: Press Return in the middle of a label. Two nodes result, with the text split at the cursor. Backspace joins them. Why: MindNode documents these behaviours (MindNode). Milestone: M3.

FR-OUT-04Should

Reorder in the outline

Dragging a line in the outline must move it, and dragging left or right must change its level. Dropping on a line must make it a child.

FR-OUT-05Should

Accept when: Filter by a word. Only matching branches and their ancestors remain visible. Why: Needed for dense maps (community); see also FR-ORG-01. Milestone: M3.

FR-OUT-06Could

Recall and review

Making or reworking a map helps memory more than viewing one, and retrieval and spacing are the best-supported techniques. This area is where the app acts on that finding. Each requirement states the strength of the supporting evidence on the evidence page. AI gap-checking is a generation task and sits on the AI engine page.

FR-MEM-01Should

Collapse-and-recall mode

The user must be able to start a recall session on a branch or whole map: the children (or labels) are hidden, the user is asked to recall them first (typed or silent), and then reveals one level at a time, marking each item as recalled, partly or missed. The results must be stored.

Accept when: Start a session on a branch of three children. Children are hidden. After revealing, mark one missed. The result appears in the review history. Why: Retrieval practice is strongly supported and beat elaborative concept mapping (evidence, strong); users already practise this by hand (community, rank 8; practice). Milestone: M6.

FR-MEM-02Should

Hidden-label mode for picture nodes

A recall session must be able to hide labels while the pictures stay, so the user names each concept from its picture, then reveals the label. It must work on picture and SVG subtrees because the label is always stored as text.

Accept when: Start a session on a picture subtree with labels hidden. Pictures show without labels and each reveal restores the live text label. Why: Pictures are cues and retrieval is the strong effect (evidence); text always stays in the tree (decision D-09; art subtrees). Milestone: M6.

FR-MEM-03Could

Blanked-node study mode

A study mode should blank a share of nodes or connection labels that the user can set (the default being roughly 30 to 40 per cent) and let the user fill them in. The share should fall automatically as the user gets items right.

Accept when: Start the mode. About a third of nodes are blank. After two sessions with all correct, the blanked share is lower. Why: Completion of partly filled maps shows a benefit in one study (evidence, weak to moderate, Chang 2002). The default share and the fading rule are proposed. Milestone: after version 1.

FR-MEM-04Should

Spaced review scheduling

The user must be able to put a branch or map on a review schedule by giving a target date. The default schedule must be expanding, with gaps of roughly 10 to 20 per cent of the time left to the target date, and every interval must be editable.

Accept when: Set a target date and the app proposes dates for the reviews. Edit one interval and the rest adapt. The schedule persists. Why: Spaced practice has strong support, and the best gap depends on the material and target date (evidence, strong, Cepeda 2008). Milestone: M6.

FR-MEM-05Could

Buzan review schedule preset

A preset must offer Buzan's reviews at about 10 minutes, 1 day, 1 week and 1 month, each using a recall from memory, with no six-month step. The interface must say that it is Buzan's schedule from Use Your Head and that the evidence supports spacing in general, not these particular intervals.

Accept when: Choose the preset and the four reviews are scheduled at those intervals. The help text states the limit of the evidence. Why: Rule 25 of the Buzan table (Buzan); the science page supports spacing but not this exact schedule (evidence). Milestone: after version 1.

FR-MEM-06Should

Review queue

A "Due" view must list the branches and maps due for review today and overdue, and each entry must open directly in recall mode. An optional macOS notification should remind the user.

Accept when: With two branches due, the view lists them. Choosing one opens its recall session. Why: Scheduling is useless without a surface that asks for the review (practice). Milestone: M6.

FR-MEM-07Should

Review history

Each recall session must be recorded with the date, branch, outcome per node and time taken, shown as a list, and optionally as a strength colour on the map.

Accept when: After three sessions the branch history lists three entries. Turn on strength colour and weak nodes are tinted. Why: Users should see their own results, and the app must show only these (no predicted retention percentage), since no evidence supports a percentage claim (evidence). Milestone: M6.

FR-MEM-08Could

Rebuild from memory

The user could start a session in which the map is hidden, build a fresh map from memory on a blank canvas, and then see the attempt overlaid on the saved map showing matched, missing, extra and misplaced nodes. Matching must at least use text comparison, and an AI judgement could be added through the AI engine.

Accept when: Rebuild a five-node branch with one node missing. The overlay marks the missing node. Why: Rebuilding from memory was better than studying in one retrieval experiment (evidence, moderate, Blunt and Karpicke 2014); gap-check with AI belongs to the AI engine. Milestone: after version 1.

FR-MEM-09Could

Explain-in-your-own-words prompts

The app could show a prompt on a chosen branch asking the user to explain it, store the answer in the node's note, and offer it again at review.

Accept when: Request a prompt on a branch. A text box opens and the answer is saved as a note. Why: Weak, indirect evidence only (evidence, weak). Milestone: after version 1.

FR-MEM-10Could

Recall as the default way back

When the user reopens a map marked as learned, the app could offer a recall session first and could say that rereading has low utility.

Accept when: Mark a map as learned, reopen it and see the offer. The user can dismiss it and choose never to see it again. Why: Recall, not rereading, is the best-supported default (evidence, strong, Dunlosky 2013). Milestone: after version 1.

FR-MEM-11Could

Session timer

The app could offer an optional timer for mapping sessions of about 20 minutes with a gentle end signal.

Accept when: Start a timer and see a signal at the end. It never interrupts typing. Why: Buzan advises mapping in short, playful bursts (Buzan); the optional status mirrors the lack of testing. Milestone: after version 1.

FR-MEM-12Later

Accept when: Deferred. Accept when selected nodes export as a flashcard file. Why: Traverse and RemNote do this (desktop tools); evidence for maps as a replacement for card review is not established. Milestone: after version 1.

Accept when: Print a large map to PDF with tiling. Why: MindNode added printing in 2026.5 but the verdict was to cover it with PDF first (MindNode verdicts). Milestone: after version 1.

Agent interface

A coding agent should be able to read the user's maps, and write to them only when allowed. Following decision D-20, the whole area comes after version 1.

FR-AGT-01Could

Command-line tool

Radiant could ship a command-line tool that lists documents, prints a map as Markdown or JSON, searches it, and validates a file. Its default must be read-only.

Accept when: Run the tool on a document while the app is closed. The tree prints as Markdown and no file changes. Why: Xmind's command-line tool lets agents read and edit local files (desktop tools). The decision brief puts the agent interface after version 1 (decision D-20). Milestone: after version 1.

FR-AGT-02Could

MCP server

Radiant could provide an MCP server (Model Context Protocol, a standard way for an assistant to call an app's tools) offering read tools for listing, reading and searching maps. It must be read-only by default.

Accept when: Connect a coding agent. It lists a map and reads a subtree but any write call is refused. Why: MindNode's MCP server is read-only by default on the Mac (MindNode, Adapt). Milestone: after version 1.

FR-AGT-03Could

Granted write access

Write tools must be enabled by the user per document, on a switch that is off by default. Writes must be applied as one undoable batch marked as made by an agent, and must preserve all branches the agent did not touch.

Accept when: Enable write for one document, let an agent add a branch, and undo it in one step. Unrelated branches are unchanged. Why: MindNode asks the user to grant write access and marks changes in its history (MindNode); Xmind validates and preserves unrelated branches (desktop tools). Milestone: after version 1.

FR-AGT-04Could

Explain MCP on first use

The first time the user turns on the agent interface, a plain-language dialog must say what MCP is, which maps are exposed, whether agents can write, and how to turn it off.

Accept when: Turn on the interface for the first time and see the dialog. It is not shown again unless requested. Why: Informed consent for access to private notes. Milestone: after version 1.

FR-AGT-05Could

Local access only

The server must be reachable only from the same machine, over standard input and output or a local socket, with no network port and no stored credentials. When the app has a document open, the tool must go through the app and never write the file directly.

Accept when: Scan open ports while the interface is on. None belongs to Radiant. Edit through the tool while the app has the file open and no corruption results. Why: Documents stay local (decision D-19; quality). Milestone: after version 1.

FR-AGT-06Later

Agent skill and schema pack

Radiant could publish a skill file for coding agents that describes the document schema and the safe edit workflow.

Accept when: Deferred. Accept when a coding agent can follow the skill to add a branch and validate. Why: Xmind installs a skill with its command-line tool (desktop tools). Milestone: after version 1.
