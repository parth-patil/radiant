WebView, Rust, Elixir and native options

This page is the evidence base for the stack decision outside Zig. Its centrepiece is a set of measurements made on your own Mac: a default system WebView is held to 60 frames per second, and the same WebView runs at 120 frames per second once one private WebKit flag is switched off, with large headroom for a mind-map-sized scene. The remaining sections cover what Elixir can and cannot do in a desktop app, what Rust offers, the native options, and a scored comparison. The recommendation itself is argued on the stack page; the Zig options are on the Zig page.

Evidence

Verified hands-on On an Apple M4 Pro running macOS 26.5.1, with the window on the built-in 120 Hz display, a default WKWebView (the system WebView that Tauri uses on macOS) ran requestAnimationFrame at 60 fps in every test. With the private feature flag PreferPageRenderingUpdatesNear60FPSEnabled set to false, every test ran at 120 fps, including Canvas2D with 5,000 tapered branches, 2,000 labels and 300 images, and WebGL2 with up to 100,000 branches. Each configuration was measured once, on one machine, with a synthetic scene.

What the measurement changes: before it, the main objection to a WebView shell was that nobody had shown it could reach 120 fps on this operating system with this kind of scene. The objection that remains is narrower. The 120 fps route depends on a private API with no public replacement and no Apple commitment, so the question becomes how much fragility is acceptable, and what the fallback is. Both questions are taken up on the stack page.

The WebView test on this Mac

The test was a hands-on spike, not a literature review. Everything in this section was measured on the developer's machine unless a badge says otherwise. Web claims that bear on the result are marked Third-party or Documented.

Method

A small Swift program (spike.swift) opens a 1400 by 900 point window containing a WKWebView, injects a test mode through a user script, receives the results through a script message handler, prints them as JSON and quits on its own after a 26 second watchdog. A separate page, spike.html, contains all the tests. Frame intervals are the differences between consecutive requestAnimationFrame timestamps, with the first 10 frames dropped, and each test runs for 3 to 4 seconds.

The synthetic scene was designed to resemble the expected workload without being a real mind map:

  • Canvas2D test: 5,000 filled, tapered, closed Bezier outlines, batched into eight colours with Path2D; 2,000 fillText labels; 300 drawImage calls of 256 by 256 pixel image bitmaps; a camera that pans and zooms continuously. The canvas had a backing store of 2800 by 1800 pixels (device pixel ratio 2). The world was 2800 by 2800 units, and the viewport showed about 16 per cent of it at zoom 1. With culling (skipping off-screen branches), about 722 of the 5,000 branches were drawn on average, about 14 per cent.
  • WebGL2 test: branches pre-tessellated into one indexed buffer (12 segments, 24 triangles per branch, drawn with a single drawElements call); the 300 images as instanced textured quads from a 4096 by 2048 atlas; the 2,000 labels from a 2048 by 2048 glyph atlas pre-rasterised at 1x, which makes them slightly soft at a device pixel ratio of 2; the camera as a uniform; multisample anti-aliasing on. The renderer string was "Apple GPU" with WebGL 2.0 and a maximum texture size of 16384.
  • WebGPU test: 10,000 instanced quads for 3 seconds.
  • Scaling probe: the WebGL2 scene with every branch drawn each frame (no culling) at 10,000 up to 400,000 branches, with the same labels and images. The synthetic branches are thin, 3 to 8 pixels wide at 1x including the taper.

Full results

The tables use the mean frame interval, not the median. WebKit rounds requestAnimationFrame timestamps to whole milliseconds, so the median prints as 17 ms at 60 Hz and 8 ms at 120 Hz, and the derived frame rate from the median (58.8 or 125) is an artefact of that rounding. The mean averages the rounding out: 16.67 ms is 60 Hz and 8.33 ms is 120 Hz. For the same reason the count of intervals over 8.4 ms is meaningless at 120 Hz, because intervals alternate between 8 and 9 ms.

The knee against the 120 Hz budget of 8.33 ms lies between 100,000 and 200,000 branches, drawn in one call with no culling and no level of detail. The knee is bracketed, not pinned. Building the tessellation (not a per-frame cost) took 7 ms at 10,000 branches and 168 ms at 400,000. The 100,000, 200,000 and 400,000 stages came from one separate run and the 10,000, 20,000 and 50,000 flag-off numbers from another, so the rows of the scaling table do not all come from a single process.

At 120 Hz with no culling, Canvas2D spent 3.5 ms of script time against an 8.33 ms budget. That figure covers only the time JavaScript spent recording drawing commands. WebKit rasterises Canvas2D work in its GPU process, off the JavaScript thread, so the completion cost is invisible in this measurement. Reaching 120 fps with no interval beyond 1.5 times the median shows that the pipeline kept up, but the Canvas2D ceiling was not found.

WebGPU

Verified hands-on navigator.gpu exists inside the embedded WKWebView on macOS 26.5.1. requestAdapter() and requestDevice() succeed. The adapter reports vendor, architecture, device and description all as "apple", a preferred canvas format of bgra8unorm, and features including timestamp-query, shader-f16, float32-filterable and several texture compression families. maxTextureDimension2D is 16384 and maxBufferSize is 2,147,483,644. Only the http://localhost/ base URL was tried; other origins such as file:// or a custom scheme like tauri:// were not tested. timestamp-query is advertised, so real GPU timing would be possible through WebGPU, but it was not used.

Documented Safari 26.0, released on 2025-09-15, enables WebGPU by default on Apple platforms, and WebKit describes it as superseding WebGL Safari 26 notes. The gpuweb implementation-status wiki lists WebKit WebGPU on macOS 26 as enabled by default gpuweb wiki. Third-party One WebKit bug report calls WebGPU on Safari 26.2 for macOS "completely unusable" for one developer's engine, reportedly fixed in iOS 26.4 beta 1; the report does not say whether the macOS fix shipped, and the details were seen only through a search snippet WebKit 301627. A second note describes the same report as WebGPU canvas flicker on Safari 26 whose status is unclear because it was marked as a duplicate.

Conditions for 120 Hz

  1. Display. The window must be on a 120 Hz display. The 60 Hz external monitor capped at 60 regardless of the flag.
  2. Timing of the flag. The private flag must be set at or before WebView creation, and the app must tolerate the flag disappearing by falling back to 60 fps.
  3. Renderer choice. Batched GPU rendering (WebGL2 or WebGPU) has far more headroom than Canvas2D. Canvas2D held 120 fps at 5,000 branches but was not pushed to its limit.

Two attempts were needed to find a working route. The first, setting the key preferPageRenderingUpdatesNear60FPSEnabled through key-value coding, found no such selector, applied nothing and left the result at 60.04 fps (the raw file for that attempt was overwritten). The second used the route taken by the tauri-plugin-macos-fps plugin: the class method +[WKPreferences _features] to find the _WKFeature whose key is PreferPageRenderingUpdatesNear60FPSEnabled, then -[WKPreferences _setEnabled:forFeature:] with false. The flag read true before and false after. A related feature key, WebAnimationsCustomFrameRateEnabled, also exists and was not touched. No public WKPreferences or WKWebViewConfiguration property raises the rate. The CADisableMinimumFrameDurationOnPhone key is iOS-only and was reported not to help in WKWebView; it was not tested.

Risk

The 120 fps unlock is a private API. It can break in any macOS update, it may raise App Store review problems, and no public replacement is promised. The route is acceptable only for software distributed outside the App Store that falls back to 60 fps when the call fails.

Caveats, as the measurement notes state them

  • Each configuration was measured once, so there is no repeat-run variance for any test. Twelve process launches were made in all. One was wasted by an argument-parsing mistake (the "prefs" word was passed as part of the mode string, so no tests ran) and one was the failed first private-API attempt.
  • Consistency evidence: across more than nine independent test stages at 60 Hz the mean interval was 16.657 to 16.671 ms, and at 120 Hz it was 8.332 to 8.338 ms, excluding the knee tests.
  • The scene is synthetic. No real text shaping or layout quality, SVG artwork, input latency, memory use, thermal throttling over minutes, hit-testing or editing was measured.
  • No GPU time was measured. The WebGL2 timer extension EXT_disjoint_timer_query_webgl2 is not exposed in this WKWebView. Script time per frame excludes GPU work and compositing.
  • No Chromium or Safari comparison was made, and no Electron build was tested.
  • Only one Mac was used (M4 Pro). Older or lower-end Apple Silicon and Intel Macs were not tested.
  • The synthetic branches are thin and do not reflect real overdraw, the cost of multisample anti-aliasing with huge fills, or the cost of rebuilding tessellation after edits.
  • Presentation latency (pointer to pixel), power and thermals were not measured.

The contradiction with the plugin README

Third-party The tauri-plugin-macos-fps README says the 60 fps cap applies to macOS 13 to 15, that "Apple removed the 60fps cap entirely in macOS 26", and that on macOS 26.3.1 a 120 Hz display and a 165 Hz external display ran at native rate with or without the plugin Plugin README. The measurement on macOS 26.5.1 contradicts that claim: a default WKWebView ran at 60 fps, and only the private flag produced 120. The notes cannot separate three possible explanations: a different build (26.3.1 against 26.5.1), a different test method, or a test that did not measure requestAnimationFrame. The Tauri issue thread observes that CSS animations and scrolling can exceed 60 Hz while requestAnimationFrame stays capped. A separate, earlier pass of the research also noted that one report said the testufo page still showed 60 fps on macOS 26.

Status of the bug and the Tauri issue

  • Documented WebKit bug 294338, "WKWebView 120 Hz", was filed on 2025-06-11 and is still NEW and unassigned, last modified 2026-09-17. It states that Safari reaches 120 Hz when "Prefer Page Rendering Updates Near 60fps" is off, and that this does not affect WKWebView WebKit 294338.
  • A comment on 2026-07-21 confirms that disabling the internal preference makes WKWebView reach 120 fps on a physical device and says the missing piece is a public embedder API. A comment on 2026-07-02 notes that Capacitor and Tauri plugins unlock 120 Hz through private WebKit API and calls this "fragile". A comment on 2025-08-18 reports that a macOS 26 Home Screen web app stays at 60 fps even with the flag off; no commenter confirms WKWebView behaviour on macOS 26 directly, so the measurement on this Mac is the first such evidence in the notes.
  • An older bug, 173434 "Support for 120Hz requestAnimationFrame", exists; it was seen only through search snippets WebKit 173434. WebKit's animation-frame-rate explainer says accelerated Core Animation animations already run at 120 Hz on ProMotion while the rest of the page updates at 60 Hz WebKit explainer. Apple pointed a forum thread on the topic to bug 294338 as the tracker Apple forum.
  • Tauri issue 13978, "Runs at only 60fps on macOS", was opened on 2025-08-10 and closed as "not planned" on 2025-08-11. A Tauri member said WKWebView does not expose settings for this. A later user reported 120 fps on macOS 15.3.1, and third-party workarounds were posted Tauri 13978. Maintainers referenced a CEF-based alternative runtime as the longer-term route; its status was not verified.
  • The Safari 26 release notes page fetched during the research returned only its title, so no release-note text on frame rate could be checked.

Re-running the test

The files are in the spikes/webview-120hz/ folder of this project: spike.swift (the host), spike.html (all tests) and results/*.json (raw outputs; results/raf_prefs.json holds only the final successful private-flag run). The flag -swift-version 5 avoids Swift 6 strict-concurrency errors in top-level code.

cd spikes/webview-120hz
swiftc -O -swift-version 5 -framework Cocoa -framework WebKit spike.swift -o spike
./spike spike.html raf            # modes: raf | c2d | gl | scale | gpu
./spike spike.html raf prefs      # add "prefs" to apply the PRIVATE feature flag
./spike spike.html scale big prefs   # scale with 100k/200k/400k branches

Elixir as a desktop app

Packaging a Phoenix LiveView app for the desktop is viable and has an official route (ElixirKit with Tauri, used by the Livebook team). Every route still needs a window shell, and the canvas has to run in client-side code. Elixir would supervise and persist, not draw. No measured start-up, size or memory figures for any Elixir desktop packaging were found in the research, and none are given here.

How the ElixirKit route starts up

  1. Rust starts a listener. A local TCP PubSub listener opens and the Elixir release is launched with ELIXIRKIT_PUBSUB set.
  2. Elixir reports ready. The release sends a ready message.
  3. The window opens. Rust opens a window pointed at the local Phoenix server.
  4. Bundling. The release is built into src-tauri/target/rel and bundled as a Tauri resource.

Documented The flow above and the signing notes (including ElixirKit.Release.codesign/1 and an entitlements file) come from the ElixirKit documentation ElixirKit docs. Third-party A community write-up runs a Burrito executable as a Tauri sidecar and opens a native WebView at localhost:4000, for macOS ARM64, Linux x86_64 and Windows x86_64. Its caveats: the window can open before the backend is ready (it polls up to 60 times at one-second intervals), migrations need manual handling, and macOS needs code signing. It gives no size, start-up or memory numbers mrpopov.com. A Tauri plus Phoenix sidecar guide skips the sidecar in debug builds, so the developer runs mix phx.server by hand during development dev.to guide.

Why the canvas runs client-side whatever the server is

At 120 Hz a frame takes 8.33 ms. A pan or zoom driven from a server would pay for serialisation, differencing, scheduling and a round trip on every frame, even on localhost. The notes mark this as engineering judgement from background knowledge and found no source for it, so it is labelled Unverified. It matches how the WebView measurement works: the measured scenes ran entirely in the page, with the camera as a uniform and no round trips. Pan, zoom and drag therefore belong in client-side code, and in a LiveView app that means a JavaScript hook owning the canvas. LiveView would carry only low-rate events such as "node text changed".

No whiteboard or canvas case study on LiveView was found; the searches returned only general Tauri plus Phoenix guides.

What Elixir would actually do

  • Supervise the Codex child process (restart on failure, back-pressure, timeouts), which is where OTP is strongest.
  • Run concurrent image-generation or conversion jobs with failure isolation.
  • Own persistence and the document operation log.
  • Fan out events to the interface through PubSub.

These gains are judgement, not measurement. The comparison point is that spawning Codex, reading its output stream and restarting on failure is a few hundred lines in Swift (Process and async streams) or Rust (Tokio), so Elixir's marginal value is supervision and the developer's fluency, not capability (the notes' own inference).

What it costs

  • A second runtime inside the app bundle, with its own release build.
  • Separate code signing for the embedded release, and notarisation through the Tauri build.
  • A Tauri or WebView shell anyway, so the Rust host is not removed, only moved behind the Elixir release.
  • Linux OpenSSL linkage caveats.
  • Start-up time and idle memory for the BEAM (the Erlang virtual machine). Unverified No 2025 or 2026 measurement of idle memory or start-up for a Burrito or Mix release was found. An old Elixir Forum post reports 48 MB of code memory in embedded mode against about 23 MB in interactive mode Elixir Forum. A secondary post claims Erlang 27 and 28 boot in 5 to 10 seconds, which it calls a "major pain point"; this was not verified and should not be relied on devbytes. A figure of roughly 60 to 100 MB in the original brief is also unverified.
Not verified

Burrito or Mix release idle memory, start-up time and bundle size; Burrito notarisation specifics; whether Bakeware is deprecated; the status of LiveView Native in 2026; how Livebook's launchers work beyond "it uses ElixirKit".

Verdict

Decision

The report keeps Elixir out of version 1 (decision D-15). The orchestration work is small: one child process, a JSON stream and a file cache. The canvas, which is most of the work, is client-side code in any case. Carrying the BEAM adds a second runtime, separate signing and start-up cost. This follows from the evidence above and from the developer's stated priority of the best app by the fastest path; it is a judgement, and the stack page argues it in full.

Elixir remains the natural choice for a later sync or collaboration server (Phoenix Channels, PubSub), where its strengths apply and no desktop packaging is involved. If the developer prefers to write the host core in Elixir anyway, the ElixirKit and Tauri route is the documented way to do it, and it leaves the canvas and the front end unchanged. Choosing it would trade the second-runtime costs above for development speed in a familiar language. The notes' own earlier ranking put the Elixir core as acceptable "if development speed and OTP supervision of the Codex child outweigh the extra signing and size cost".

Tauri and Electron

Tauri 2 is a Rust host process around the system WebView, and Electron bundles Chromium and Node. The measurement on this Mac shows that the system WebView on macOS can reach 120 fps with a private flag, so the question for Tauri is fragility and per-platform WebView differences, not the macOS performance ceiling. For Electron the notes have no measurement at all.

Architecture and versions

  • Tauri 2.11 shipped in July 2026. Electron 44 went stable on 25 August 2026 on Chromium M152 Better Stack.
  • Tauri uses the operating system's WebView: WKWebView on macOS, WebView2 (Chromium-based) on Windows and WebKitGTK on Linux. This is what makes it small, and it is also why behaviour differs by platform.
  • Any Tauri shell on macOS would need the same private call as the community plugin, or a patched wry (Tauri's WebView layer), and would inherit its fragility. The plugin tauri-plugin-macos-fps flips the flag through private +[WKPreferences _features] and -[WKPreferences _setEnabled:forFeature:] calls, guarded by respondsToSelector checks Plugin source.

  • macOS: WKWebView, measured above: 60 fps by default, 120 fps with a private flag. A Babylon.js forum thread discusses a performance gap between Safari and Tauri's WKWebView; its details were not read Babylon forum.
  • Windows: WebView2 is Chromium-based, so rendering behaviour is closer to Electron's. The notes gathered no frame-rate measurements for it.
  • Linux: WebKitGTK. The notes mark Linux WebKitGTK behaviour as unverified, and the decisions brief treats it as the weakest target that may need an Electron build instead.

Sidecars, plugins and what is unmeasured

Tauri supports sidecar processes, which is how a Burrito executable or a Codex child could be run, and has a plugin ecosystem. The notes did not verify Tauri's raw binary and custom-protocol throughput, sidecar specifics or the state of Tauri mobile.

Electron is the safe rendering baseline in principle (Chromium, WebGPU, and the WebKit bug thread remarks that Chrome and Firefox can run requestAnimationFrame at 120 fps), at the cost of the sizes above and two to four times the idle memory. Unverified No source found in the research describes Electron on ProMotion directly, and no Electron build was tested. The WebView spike page can be run unchanged in an Electron host, which is the missing measurement, and the decisions brief calls for it before any public release. No measured canvas or WebGL comparison between WKWebView and Chromium was found either. A rigorous published canvas benchmark does not exist in the notes; only general blog comparisons were found, and two benchmark repositories (js-game-rendering-benchmark, pixijs-rendering-comparison) were seen but not mined for numbers.

Native Rust interfaces

A native Rust canvas has the highest ceiling and the least dependence on a WebView, and also the largest amount of non-canvas work: text editing, input methods, menus and accessibility. Every framework below is either pre-1.0, stagnant or conditionally licensed, and none has a published measurement for thousands of Bezier paths. All version numbers and dates in this section come from the crates.io API and GitHub release pages as read on 2026-11-17.

Risk

No frame-time measurement exists in the notes for "5,000 tapered Beziers at 120 Hz" in any Rust renderer, and no published Vello against Skia comparison for path-heavy scenes was found. The canvas ceilings given for these stacks in the matrix are judgement, discounted where behaviour is unmeasured.

GPUI in more detail

Documented From the source: elements/canvas.rs offers canvas(prepaint, paint) as a "low level paint API" canvas.rs. path_builder.rs builds paths on lyon_path with fill and stroke options (width, cap, join, miter limit) path_builder.rs. elements/svg.rs provides an svg() element from a path or bytes svg.rs. input.rs defines EntityInputHandler with UTF-16 ranges, marked-text and bounds methods for native text services, the hook an input method needs input.rs. The README links an accessibility topic. A separate gpui_platform crate is used with features per platform: macOS needs font-kit for glyphs, Linux needs wayland and or x11, Windows needs none.

Documented Zed's blog reports a stable 120 fps on an M1 MacBook Pro ProMotion display with render time under 4 ms. Dropped frames came from ProMotion downclocking, not render cost. The fixes were a display-link callback, presenting every frame for one second after the last input, and a triple-buffered instance-buffer pool; calling present_drawable before commit with presentsWithTransaction disabled gave a stable 120 Zed 120fps. GPUI's design is "video-game style" GPU rendering of UI primitives, with shadows drawn using Evan Wallace's technique Zed GPU.

Not verified

GPUI's retained-path behaviour, image texture caching, mipmapping, paint_path batching and zoom behaviour; any infinite-canvas example; whether menus and file dialogs are native on Windows and Linux. The notes infer that PathBuilder tessellates through lyon on each paint call, so thousands of tapered branches would need cached Path objects or a custom pipeline. This is why GPUI's canvas ceiling is scored as unproven, not 5. Earlier research could not tell whether a stable crate existed; the crates.io listing above corrects that, though the version is still 0.x.

egui, winit and the macOS gaps

Third-party The egui case study the notes rely on is Tritium, a legal desktop app. It reports that immediate mode rebuilds the UI every frame, which costs power on laptops, and that business logic leaks into UI code. winit issue 4458 blocks access to the native macOS NSApplication delegate (open-with and URL handlers) and is fixed only in winit 0.31, still in beta (0.31.0-beta.4, 2026-10-24). No clean statement of egui's current IME quality was found.

Third-party The clearest "egui panels plus a custom wgpu viewport" example is Rerun. Swift and a portable core

A native Swift shell (AppKit with Metal) gives first-party text editing, input methods, menus, accessibility and updates, and no WebView frame-rate cap. It reaches other platforms only by writing a new shell for each, unless a portable core is placed underneath. The notes found no published frame-time comparison for a Swift and Metal canvas at this workload and no internals for MindNode, Freeform, OmniGraffle or Sketch.

What the sources support

  • MindNode's site says it uses AppKit, UIKit and SwiftUI together and calls itself 100 per cent native MindNode site. The Ghostty pattern

Documented Ghostty has a Zig core exposed as a C library, a Swift and AppKit shell on macOS and GTK4 on Linux, delivered as a static library and an XCFramework. Its author says any language with a C ABI, including Rust, works for the core Hashimoto. For Radiant, the same pattern with a Rust core would keep the document model, layout, spatial index and tessellation reusable on Windows and Linux. The bridge would be UniFFI for the model and command interface and a raw C ABI or shared memory for per-frame draw lists. The shell could render either with Metal from vertex buffers produced by the core (best macOS result, a new renderer per platform), or the core could render with wgpu or Vello into a surface the shell hosts (one renderer, but the GPU Vello variants are still maturing). The Zig variant of this pattern is on the Zig page.

What it gives and what it costs

Gives

  • No WebView cap and no private API; ProMotion through CADisplayLink (inference, not sourced).
  • First-party text input, IME, menus, accessibility, notarisation and updates (Sparkle), mostly background knowledge.
  • A small footprint: in one same-app comparison, a 10 MB DMG.
  • An escape hatch if the WebView ever limits the app (decision D-17).

Costs

  • The Metal tessellation and glyph pipeline is the developer's to write (inference).
  • Core Graphics CGPath.copy(strokingWithWidth:) gives only constant-width strokes, so tapered ribbons would be built as polygons from offset curves (inference).
  • Swift and Metal are new languages and a new pipeline for this developer, and a second language beside Rust if a Rust core is used.
  • SVG artwork support: native libraries do not match the browser engine (see the rendering section).
  • Effort: the notes' own estimate is 3 to 5 months to a good macOS MVP for a developer new to Swift and Metal, more for other platforms. This estimate is not sourced.

How it would reach Windows and Linux: a new native shell per platform (the Ghostty route), or the core drives its own wgpu window. In the notes' pass 2 ranking, a Swift shell with a Rust core came first and a Swift shell with a Zig core ranked near the bottom because Zig 0.16 and 0.17 both broke APIs and ZLS was broken on 0.17. The notes' reasoning for Rust over Zig as a core language is the currency of the Rust building blocks listed above.

Third-party PixiJS v8's published figures (2024): CPU time for moving 100,000 Bunnymark sprites dropped from about 50 ms to about 15 ms and GPU time from about 9 ms to about 2 ms PixiJS v8 beta. Text and SVG

The WebGL2 test pre-rasterised its 2,000 labels into a glyph atlas, which is the usual route and the source of the softness at 2x. Real text shaping and layout quality was not measured. For SVG, the browser engine is the most complete renderer available to this app: generated artwork can use gradients, clipping and filters that the small native SVG libraries do not support, and resvg's coverage was not verified. That is a main reason the report favours a web stack, as the picture and SVG subtrees page explains. SVG rendering speed in the WebView was not measured; the plan to rasterise visible SVG subtrees to textures per zoom bucket is a design, not a result.

Not verified

CanvasKit and Skia compiled to WebAssembly, Rive, Konva, Fabric, Two.js, React Flow, markmap, OffscreenCanvas with workers, createImageBitmap practice, and SVG-to-texture rasterisation practice were not researched. The notes' hypothesis that a WebGL2 renderer with cached branch meshes, atlas or per-image textures with mipmaps and spatial-index culling fits the budget is partly confirmed by the measurement for branches, and untested for mipmapped per-image textures, real text and edits.

What this means for Radiant

Implication for Radiant

The evidence supports a WebView shell with a WebGL2 canvas as the fastest path that still reaches 120 fps on your Mac. The case rests on four measured or documented facts: the default WebView is capped at 60 fps; one private flag lifts the cap; WebGL2 has 20 times the branch count of the 5,000-branch reference map (100,000 at 120 fps) with no culling or level of detail; and the browser engine is the most complete SVG renderer available. The stack page turns this into the decision.

  • Frame rate: treat 120 fps as achievable on a ProMotion display through the private flag, treat 60 fps as the guaranteed floor, and detect the flag's absence at start-up and fall back. Show no 120 fps promise on external 60 Hz displays.
  • Renderer: WebGL2 for branches and images first. Keep Canvas2D for simple overlays. Plan WebGPU as a later backend, since it works in the WebView but only a trivial scene was tested.
  • Budget: the 5,000-node reference map sits far below the measured knee. The stress map of 50,000 nodes is inside it for branches alone, but images, real text and edit-time rebuilds were not measured.
  • Shell: Tauri is the smallest option and the Electron comparison is unmeasured, so an Electron build of the spike should be run before any public release. All host calls should sit behind one interface so the shell can be swapped.
  • Elixir: not in version 1. Keep the ElixirKit route in reserve if the host core is later preferred in Elixir, and use Elixir for any later sync or collaboration server.
  • Escape hatch: a Swift shell with a Rust core, using the Ghostty pattern, is the documented fallback if the WebView ever limits the app. Keeping the model, layout and tessellation in pure modules keeps that path open.
  • Native Rust frameworks: none is recommended for the shell on the present evidence. GPUI and Xilem are pre-1.0, egui has macOS gaps, Slint is licence-gated and the winit, wgpu and Vello route is a multi-month build.

Limits of this research

  • One run per configuration, on one M4 Pro Mac with a 120 Hz built-in display, with a synthetic scene. No repeat variance, no older or Intel Macs.
  • No Electron or Chromium measurement, no comparison with Safari, no input latency, no memory or thermal data, no GPU timing, no real text, SVG, hit-testing or editing.
  • Whether macOS releases other than 26.5.1 behave the same way was not tested. The plugin README claims no cap on 26.3.1 and the measurement contradicts it on 26.5.1; the reason is unresolved.
  • No start-up, size or idle-memory figures for any Elixir desktop packaging. Tauri and Electron figures are vendor-adjacent or single-author and disagree with each other.
  • No frame-time evidence for thousands of tapered paths in GPUI, egui, Vello, Flutter, Qt, Compose, Avalonia or Swift and Metal. No Vello against Skia comparison.
  • Not verified: egui and iced IME quality on macOS, Slint and Makepad text editing, Slint's royalty-free licence terms, Qt Quick LGPL status in 6.11, GPUI image and path caching, resvg coverage, macOS notarisation and universal-binary specifics beyond Sparkle's version and ElixirKit's notes, how MindNode, Freeform, OmniGraffle and Sketch are built.
  • Effort estimates for native builds are the researchers' judgement. The notes gave no person-month figures from any case study.
  • Comparison scores are judgement and should be re-checked after spikes on the shortlisted stacks (Metal from Swift, Tauri with a WebGL2 canvas, Flutter CustomPainter) on your own Mac.
