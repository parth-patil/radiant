The stack decision

Build Radiant as a Tauri application: a Rust host process around the system WebView, with the map drawn by a small purpose-built WebGL2 renderer written in TypeScript. A test on your own Mac showed that this combination holds 120 frames per second with twenty times the 5,000-branch map this report uses as its reference. It is also the only option in which the generated SVG artwork, the app's signature feature, is rendered by a complete SVG engine at no cost to you.

Decision

Shell: Tauri 2 (Rust). Interface and engine: TypeScript, with Svelte for panels. Canvas: custom WebGL2 renderer, WebGPU later. Host core: Rust, owning the Codex process, the document file and the image cache. AI: one long-lived codex app-server child process. Zig: not in the shell or interface; a candidate for small WebAssembly kernels later. Elixir: not in version 1; the natural choice for a sync server later.

The recommended stack

Each layer below is chosen so that the layer above it does not depend on how it is built. That is what lets the shell or the renderer be replaced later without touching the rest.

Interface panelsSvelte 5 components in ordinary HTML: outline, inspector, style editor, prompt bar, dialogs. HTML supplies text editing, input methods for languages such as Hindi, Japanese or Chinese, accessibility and keyboard handling without any work from you.
Engine corePure TypeScript modules with no browser or graphics dependencies: document model and undo log, layout, branch geometry, spatial index, hit-testing. They run in a background worker and can later be ported to Rust or Zig compiled to WebAssembly if profiling ever demands it.
RendererA WebGL2 renderer of a few batched draw calls: one mesh for all branches, textured quads for pictures, glyph quads for labels, overlays for selection. It sits behind a narrow interface so a WebGPU backend can be added.
Host interfaceOne small TypeScript module through which the front end reaches the host: open and save, start a generation, cancel, receive streamed events, fetch an asset. Nothing else in the front end knows that Tauri exists.
Host coreRust inside the Tauri process: supervises the Codex child process, reads and writes the SQLite document file, keeps the content-addressed image cache, and does background image work such as thumbnails and background removal.
AI engineThe Codex command-line tool you already have, started as codex app-server and driven over standard input and output with JSON-RPC messages. It uses your existing ChatGPT login; the app never reads the credential file.

Why this stack

It is fast enough, by measurement

The doubt about any WebView design is frame rate. Instead of arguing about it, a test program was built and run on your Mac (Apple M4 Pro, macOS 26.5.1, built-in 120 Hz display). The full method and every number are on the options page. The summary is below.

120 fpsCanvas2D with 5,000 tapered branches, 2,000 labels and 300 pictures, using about 3.5 ms of script time per framePrivate WebKit flag switched off
100,000Branches held at 120 fps by a batched WebGL2 scene, with the same labels and pictures2.4 million triangles, no culling
60 fpsThe cap on a default WebView in every test, whatever the drawing methodNo public setting raises it
1 runEach configuration was measured once, on a synthetic sceneTreat as strong direction, not a guarantee

Your target is a few thousand nodes. The measured ceiling is one to two orders of magnitude above that, which leaves room for real content to be heavier than the synthetic scene and still hold the frame budget.

The signature feature needs a real SVG engine

Radiant will ask a language model to draw SVG artwork for a subtree. Models use whatever SVG features suit the picture: gradients, clipping, masks, sometimes filters. A browser engine renders all of it correctly. The small SVG libraries a native app would embed do not. The research found that nanoui's own rasteriser does not draw text, images, patterns, filters or markers, and that resvg, the usual Rust choice, renders static SVG only and has no system text rendering (details on the Zig page and the engine page). In a WebView the best SVG renderer available is already there, and the picture subtrees get image decoding for every common format in the same way.

It is the fastest path to a complete app

A mind-mapping app is half canvas and half ordinary interface: an outline panel, an inspector, text fields, menus, dialogs, drag and drop. In a native Zig or Rust interface most of that must be built or patched, and text entry with input methods is the hardest part. In a WebView it exists. The researcher who assessed the Zig options estimated two to four months to a first usable version for a WebView design, three to five for a Zig core with a Swift shell, and nine to fifteen months or more for a pure Zig interface. Those are estimates, but the ordering matches your stated priority of the best app by the fastest path.

It reaches other platforms without a rewrite

The whole front end, which is most of the code, is the same on every platform. On Windows, Tauri uses WebView2, which is Chromium. Linux is the weak spot, because Tauri uses WebKitGTK there. If Linux matters later, ship that platform as an Electron build of the same front end.

The choice is cheap to reverse

Because the front end reaches the host through one interface, replacing Tauri with Electron is a matter of days. Because the engine core has no browser dependencies, it can move to WebAssembly or, in the worst case, sit behind a native renderer. The decision that would be expensive to reverse is the opposite one: committing to a native interface toolkit before knowing whether its text editing and SVG handling are good enough.

The 120 Hz question

The test produced one uncomfortable fact, and the decision has to face it. A default system WebView on macOS 26.5.1 draws at 60 frames per second, even on a 120 Hz display. It reaches 120 only when a private WebKit feature flag, PreferPageRenderingUpdatesNear60FPSEnabled, is switched off when the WebView is created. No public setting does the same thing; the WebKit request for one is still open.

Zig, Elixir and Rust

Zig

Not for the shell or the interface

The library you asked about is justrach/nanoui, four weeks old at the time of writing. Its canvas has straight lines, polygons and circles, with no Bezier curves and no variable-width strokes, so it cannot draw tapered branches. Its image atlas has no mipmaps, and its interface is allowed to change at every minor release. Zig itself removed @cImport and reworked its build system in the version you have installed.

Zig fits well as the language of a small, self-contained kernel compiled to WebAssembly, such as the branch tessellator. That gives you real Zig work with a narrow surface exposed to toolchain changes. See the Zig page.

Elixir

Not in version 1

A LiveView app packaged with Burrito has no window of its own, so it still needs a WebView shell. The canvas must run in client-side code whatever the server is. That leaves Elixir supervising one child process and a file cache, which is a few hundred lines in the host's own language. The price would be a second runtime, separate code signing of the embedded release and extra start-up time.

Elixir becomes the right tool the day Radiant needs a sync or collaboration server. If you would rather write the host core in Elixir anyway, the Livebook team's ElixirKit with Tauri is the supported route. See the options page.

Rust

Yes, in a small amount

You asked whether there is a good reason to use Rust. There is: Tauri's host process is Rust, and the host work here is modest and well served by mature libraries for processes, SQLite and images. You do not need a Rust interface toolkit. The same Rust core would also carry over if the app ever moved to a native shell.

When to change course

The recommendation rests on a measurement and several judgements. These are the signals that would overturn it, and what to do in each case.

SignalResponse
The private flag stops working after a system updateThe app falls back to 60 frames per second automatically. Measure an Electron build; if it reaches 120, ship Electron on macOS.
Real maps miss the frame budget after optimisationMove the measured hot spots of the engine core to WebAssembly, then move the renderer to WebGPU. Only if both fail, start the native shell.
Input latency in the WebView feels wrong and cannot be tunedThis was not measured. Test it in the first spike. A native shell is the only full fix.
You decide to distribute through the Mac App StorePrivate settings are not allowed there. Ship at 60 frames per second, or use Electron, or build the native shell.
WebGPU becomes stable in the system WebViewAdd it as a second renderer backend; nothing else changes.
nanoui gains curved paths, mipmapped images and a stable interfaceReconsider it for a native build. The signals to watch are listed on the Zig page.

What to verify first

Four short experiments remove most of the remaining uncertainty before any product code is written. They are the first milestone on the roadmap.

  1. Repeat the frame-rate test inside a real Tauri 2 window, with the flag switched off at WebView creation, and with the automatic fallback.
  2. Run the same test page in an Electron window to learn whether Chromium reaches 120 frames per second on your display without any private setting.
  3. Measure input latency for pan, zoom and drag in both shells.
  4. Draw a real map: 5,000 nodes with actual labels and 300 generated pictures, using the first version of the renderer, and check the frame budget.

The Codex side needs no further proof of feasibility. Streaming, structured output, image generation with transparency and contract-conforming SVG were all exercised on your installed version; see the Codex page.
