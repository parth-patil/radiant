Research and requirements · 23 November 2026

Radiant agent tooling: a CLI and programmatic surface that lets AI agents draw any mind map

This document works out what the tooling should be. It starts from what the repository already ships, compares it with how other diagram and canvas tools expose themselves to agents, and ends in numbered requirements, architecture options and a phased plan. Nothing here is built unless it is marked Built. Source baseline: commit f909c4a on master.

1 · Summary

Summary and recommendation

The goal, in the owner's words

“I want a very powerful cli tool / programmatic tooling for the mind map exposed so that AI agents can drive it and draw any mind maps.”

Where Radiant is today. A Bun CLI (tools/agent-cli.ts) and a stdio MCP server read saved maps as Markdown or JSON, search them and validate them. With an explicit 15-minute grant from the Inspector, an agent can read the live state of one open map and apply three kinds of text edit to it: add a child, rename, set a note. All six agent requirements in requirements/features.md (FR-AGT-01 to 06) are recorded as Verified.

The gap. An agent can read any map and annotate one open map with text. It cannot create a map, style it, choose a layout or theme, attach a picture, move or delete anything, render an image, or see what the result looks like. The core library already models all of those things; none of them are reachable from outside the app.

Recommendation in ten points

  1. One tool with three faces. Grow the existing CLI into a single radiant command with a stable JSON envelope. The MCP server and the skill call the same command table, so there is one vocabulary to learn, document and check.
  2. Declarative first. Add a map spec: a Markdown outline with a small front-matter header, {…} attribute blocks and a links block. Any outline that Radiant imports today is already a valid spec. One command, radiant build, turns a spec into a finished, styled map. The agent states structure and intent; the engine computes all geometry.
  3. Imperative second, on the model that exists. Widen the three-edit batch into a full patch vocabulary (add, move, delete, style, layout, theme, links, pictures). Every spec and every patch compiles to the existing Op and Transaction types, so undo, the journal and change attribution keep working unchanged.
  4. Two back ends behind one interface. A closed file is written through a store writer; a map open in the app is written through the existing grant socket. One writer at a time: if a window owns the file, the CLI must go through the app.
  5. Structure before pixels. Give agents a layout report and a lint (boxes, bounds, overlaps, wrapped labels, balance, contrast) as JSON. It is cheap in tokens and exact. Rendered images come second, sized for vision models (long edge 1,568 px by default).
  6. Render by reusing the export path. The exact engine is the running app's own exporter. A headless engine (the SVG builder plus a text measurer and an SVG rasteriser) covers the case where no app is running, and says in its report that its text metrics are approximate.
  7. Live control on the same socket. Selection, reveal, camera, export and a change stream join read and edit. No TCP listener is added. The grant should survive closing the Inspector and show a visible indicator while active.
  8. Safety by default. Read-only unless granted; consent per map; write and destructive tiers granted separately; revision preconditions; dry run; one Undo step per batch; an audit trail in the operation log.
  9. Introspection built in. radiant capabilities, schema, themes and examples let an agent discover the surface at run time. Errors name the valid values and the nearest matching id.
  10. Ship in phases. Foundations and read commands; then spec and build; then the full edit vocabulary; then visual feedback; then live control; then packaging. Section 7 gives effort estimates, labelled as estimates.
Why this order

The single largest jump in what an agent can do comes from build plus lint: a whole styled map from one file, checked without a screenshot. It needs no change to the desktop app if the first output target is the portable bundle that Radiant already imports, and one decision (section 8, D2) if it should write .radiant files directly.

The live path and its limits

Grant scope
One canonical file path, one document id, one owning window. A second grant replaces the first (AgentAccess holds a single Option<Arc<Grant>>).
Lifetime
15 minutes (TTL), or until revoked, or until the Inspector or the map closes. The recorded acceptance run did not wait for expiry (FR-AGT-03, remaining gap).
Channel
A Unix socket at $TMPDIR/radiant-agent-<16 hex>/write.sock in a directory created with mode 0700, plus a 32-hex token. No TCP listener in the app or in the MCP process (FR-AGT-05 evidence).
Consent
An explanation dialog on first use; writes are off by default; the user copies four RADIANT_AGENT_* values into the agent's environment by hand.
Attribution
Edits are tagged {ai: 'agent:<id>'}; describeChange reports them as source agent, and the operation log keeps forward and inverse operations.

Assets the new tooling should build on

Op and Transaction model

Eleven JSON op types, each returning its exact inverse; applyOps restores the document if any op throws. A batch is one labelled Transaction with a source.

src/lib/core/types.ts, core/model/ops.ts, editor.ts

Command helpers

More than twenty pure functions that turn an intent into ops: addChild, moveSubtree, deleteSubtree, setStyle, addLink, insertOutline, duplicateSubtree and others.

src/lib/core/model/commands.ts

Interchange parsers

Markdown, indented text, OPML, FreeMind, JSON Canvas, Xmind, MindNode and the portable bundle, each reporting what it skipped.

src/lib/core/io/, core/model/outline.ts

Pure layout and geometry

Layout takes node sizes from an injected MeasureFn, so it runs anywhere a text measurer exists. The scene pipeline is documented as pure TypeScript.

src/lib/core/layout/, core/geometry/style.ts, ui/pipeline.ts

Journal with digests

Each commit stores the snapshot, the index rows and an operation-log entry in one SQLite transaction. The SHA-256 of the exact document string is a ready-made revision token.

src-tauri/src/store/mod.rs, journal.rs, projection.rs

A streaming contract for models

The in-app AI already uses a JSON Lines node stream that ignores geometry fields and applies nodes as they arrive, grouped into one Undo step.

src/lib/core/ai/stream.ts, templates/node-stream.json

Native store without the UI

The format-compatibility gate builds a scratch native binary that calls the production store directly. That is a precedent for a small store helper.

tools/check-format-compat.py, tools/fixtures/formats/README.md

Capture harnesses

A Chromium-driven browser host and an off-screen WKWebView capture script already exist for the browser and visual gates.

tools/check-browser.py, check-visuals.py, visual-webview.swift

Protocol, packaging and CLI practice

Model Context Protocol, revision 2026-07-28

  • The current revision is 2026-07-28. It removes the initialize handshake and protocol-level sessions; servers that need state across calls return explicit handles that the client passes back as tool arguments. tools/list must not vary per connection.1 2
  • Roots, Sampling and Logging are deprecated; pass files or directories as tool parameters or server configuration instead.4
  • A tool may declare an outputSchema and return structuredContent, mirrored as text for older clients. Validation failures go in the result with isError: true so the model can correct itself. Results can carry image blocks and resource links.3
  • Annotations (readOnlyHint, destructiveHint, idempotentHint, openWorldHint) are hints, not enforcement.9
  • For local servers the spec recommends stdio; a loopback HTTP port is not an authentication boundary and needs a token and Origin validation.7 8 6
  • stdio servers must write nothing but protocol messages to stdout.5 Client guidance recommends loading tool definitions progressively once they take more than a few percent of the context window.10
  • Claude Code warns when a tool result passes 10,000 tokens and caps it at 25,000 by default; image results count against the same cap.11

Agent Skills and the CLI-versus-MCP question

  • A skill is a directory with SKILL.md (front matter name and description) and optional scripts/, references/ and assets/. The spec recommends a body under 500 lines with detail pushed into references.14
  • Claude Code reads skills from ~/.claude/skills and .claude/skills;15 Codex reads .agents/skills up the tree and $HOME/.agents/skills, with optional agents/openai.yaml metadata.16
  • Token cost: one comparison measured 1,421 input tokens for a CLI, 3,315 for a skill and 23,228 for a two-tool MCP server on a single task, with most of the MCP cost coming from one large tool result. Vendor claim17 Another found the gap mostly closed now that clients load tool definitions lazily. Vendor claim18 A third reports 150,000 tokens falling to 2,000 when MCP servers are presented as code APIs. Vendor claim13 All three are single-scenario measurements.
  • Guidance for tool design: a few workflow-shaped tools, clear names, a concise or detailed response switch, and errors that say how to fix the call.12

CLI design for agents

  • Long-standing guidance: data on stdout, messages on stderr, --json, meaningful exit codes, never require a prompt, --dry-run, accept - for stdin, idempotent where possible, suggest a fix when the input is nearly right.19
  • Agent-specific additions from 2026 write-ups: raw JSON input, a schema command for run-time introspection, field masks and bounded output with a truncation hint, input hardening against control characters and path traversal, errors that list valid values, a single response envelope, and shipping the skill and an MCP mode with the same CLI.20 21 22 23

Visual feedback and local control

  • Browser automation servers default to a structured snapshot and treat pixels as opt-in. Playwright MCP returns an accessibility tree with refs and can add [box=x,y,width,height] per element; Chrome DevTools MCP says to prefer a snapshot over a screenshot.75 76
  • Image cost for Claude is ⌈width / 28⌉ × ⌈height / 28⌉ tokens; images are downscaled past a 1,568 px long edge on the standard tier and 2,576 px on the high-resolution tier.52
  • Claude Code's guidance is to give the agent a check that comes back pass or fail, with a screenshot beside the target as one example.54
  • Vision is weak on small targets: the best model in one benchmark of high-resolution professional screens located 18.9% of targets.50
  • Local control channels have a poor security record when they use loopback HTTP or WebSocket without authentication: MCP Inspector (CVE-2025-49596), Claude Code IDE extensions (CVE-2025-52882) and the MCP TypeScript SDK's DNS-rebinding default (CVE-2025-66414).88 89 90
  • Tauri deep links are one-way and can be triggered by anyone; on macOS they cannot be registered at run time.84 Tauri has no WebDriver for WKWebView on macOS.86

Lessons for Radiant

  1. Structure in, geometry out. Every tool that works well keeps coordinates away from the model (auto-layout, relative placement, lints). Radiant's own node-stream contract already ignores geometry fields. Keep that rule.
  2. Use a format models already write. Markdown outlines are close to a solved output format; a new indentation DSL is a measured risk. Radiant's importer already reads Markdown, so the cheapest reliable path is to extend it.
  3. Pure outline languages stop at the tree. Mermaid, Markmap and PlantUML have no cross-links and little per-node style. The spec needs ids and attributes to reach the rest of Radiant's model.
  4. Echo what was parsed. Return node count, depth and assigned ids after every write, with line-anchored errors and warnings. Silent re-parenting is the failure to design against.
  5. Return ids and fail loudly on stale ones. Return the id of everything created; reject unknown ids with the nearest match and a hint to re-read.
  6. Offer both bulk and atomic edits. A whole map or branch in one call, and single-node operations for small changes.
  7. Structure first, pixels on request. A layout report and a lint are cheaper and more precise than a screenshot. Size images for the model and allow a branch crop, because small text is where vision fails.
  8. Ship the format guide with the tool. A skill, plus a schema and examples command, loaded once per session.
  9. Local means stdio and a Unix socket. Radiant already does this. Do not add a loopback HTTP port.
  10. Gate writes and deletes separately, and make agent edits undoable. MindNode's write toggle and Miro's consent-gated deletion are the precedents; Radiant already applies each agent batch as one Undo step.

5 · Proposal

Proposed tool surface

Six rules shape everything below.

  1. One command table, three transports. The CLI, the MCP tools and the skill examples use the same verbs, arguments and JSON.
  2. The agent states structure; the engine computes geometry. No coordinates in the default path.
  3. Every write is a Transaction of existing ops. No second document model.
  4. Read-only unless granted, and one writer at a time.
  5. Structure before pixels when reporting back.

Rules that make the format safe for a model to write.

  • Compatible by construction. A file with no front matter, no attribute blocks and no links block parses exactly as the Markdown importer parses it today. Two new readings need an escape: a label that ends in a literal {…}, and a list item that starts with [ ] or [x].

  • Streaming stays on the existing contract. For progressive drawing into an open map, the compiler emits the same node stream the in-app generator uses. No third format.

The reply names what was created, so the next batch needs no re-read.

Stable ids
Ids never change once assigned. A reply maps every ref (and the position of every unnamed add) to its new id. A stale or misspelt id fails the whole batch and returns the nearest matches.
Transactions
One batch is one Transaction with a label and the source agent:<client>:<tx>. It is atomic: applyOps already restores the document if any op throws. For changes larger than one frame, tx begin returns a handle, later batches name it, and tx commit closes it; in the app this maps to Editor.beginGroup, which is how streamed generation becomes one Undo step today.
Preconditions
ifRevision carries the SHA-256 of the document string, which the store already computes (document_digest) and already checks before a commit (commit_edit takes the expected digest). A mismatch returns a conflict with the current revision and applies nothing.
Dry run
--dry-run compiles and applies to a clone, then returns the same result shape with "status": "dry_run", the op count, the ids that would be created and the lint difference. Nothing is written.
Undo
On a live map, undo --tx calls Editor.undo only if that transaction is on top of the undo stack; it never reverts a user edit. On a file, it applies the inverse ops recorded in operation_log as a new entry. The log keeps the most recent 1,000 entries (journal.rs).
Limits
Today: 32 edits, a 64 KiB frame, 1,000 bytes of label, 8,000 bytes of note, enforced in three places. Proposed: one shared schema, and limits sized for a whole-branch insert (for example 2,000 ops per transaction through a transaction handle).

Same-user boundary

The socket directory is private to the user and the token is random, so the control against other local processes is the secrecy of the token. 7 · Architecture

Architecture options and a phased plan

Where the logic runs

Option A · Pure TypeScript core in a Bun CLI

How the CLI works today

  • For: reuses core/model, core/io and core/layout directly; starts fast; needs no app and no display; keeps the “core is pure” rule and its boundary check.
  • Against: the Rust store owns the file format (index rows, sibling order keys, journal). Writing files from TypeScript means a second implementation of that. Text measurement needs a replacement for the browser canvas.

Option B · Call the Rust host

A small native helper built from radiant_lib

  • For: one implementation of the format, the durability settings and the journal. The format-compatibility gate already builds a native binary that calls the production store without the UI.
  • Against: a second shipped binary to build, sign and version; store functions must be callable without Tauri state; no help for layout or rendering, which live in TypeScript.

Option C · Drive the app over the socket

The app does everything, the CLI is a remote control

  • For: no duplicated logic at all; rendering and text metrics are exactly what the user sees.
  • Against: needs the app installed, running and a desktop session; cannot run in CI or a container; the app would need a no-document service mode to work on closed files; start-up cost on every cold call.
Recommendation

A for logic, B for durable file writes, C for exactness. Spec compiling, op compiling, queries, lint and the layout report run in the pure core (A). Committing to a .radiant file goes through one store implementation (B), so there is a single owner of the format. The running app (C) is used when the map is open, for edits, and whenever an exact render is wanted. This keeps every existing boundary: core/* stays pure TypeScript, host/ stays the only Tauri importer, and the Rust store stays the only code that lays out a file.

One op schema instead of three validators

The three edit types are declared and checked in tools/agent-write.ts (zod), src-tauri/src/agent_access.rs (a Rust enum with deny_unknown_fields) and src/lib/ui/AgentAccess.svelte (hand-written checks). Widening the vocabulary to Table 8 in all three would triple the work and invite drift. The proposal: define the op schema once in core/; the CLI and the app's web side both validate with it; the Rust host stops interpreting edits and enforces only what it is placed to enforce (token, document id, path, grant tier, frame size, rate), passing the validated JSON through. Tier enforcement needs the host to know whether a batch is destructive, which the request can declare and the web side can verify.
