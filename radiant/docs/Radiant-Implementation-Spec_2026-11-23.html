Radiant implementation spec

Everyday themes, presentation, Excalidraw-style canvas drawing and agent tooling. Written on 23 November 2026 to be handed to implementing agents. It states what to build, the decisions already taken, the shared types, the acceptance check for every requirement and the order of work.

1Read this first

This document tells an implementing agent what to build in Radiant, a local-first macOS mind-map editor in radiant/ (Tauri 2 with a Rust host, Svelte 5 with SvelteKit, TypeScript, a custom WebGL2 renderer, single-file SQLite documents).

It covers four workstreams. Each has numbered requirements with an acceptance check, the files that change, and a place in the build order.

WorkstreamIdsWhat the owner getsSection
Everyday themesTHM-Six new themes (Daylight, Studio, Sorbet, Citrus, Lagoon, Boardroom), each with a dark variant, and the drawing features they need.§5
PresentationPRS-Present a map to a team: step from node to node, reveal subtrees with animation, keep context dimmed, save storylines, speaker notes, a presenter screen, PDF handout.§6
Canvas drawingCNV-Excalidraw-style drawing on the infinite canvas: shapes, sticky notes, arrows, freehand, text and frames beside the mind maps, with .excalidraw import and export.§7
Agent toolingAGT-One radiant command that AI agents call to build, edit, inspect, lint and render maps, and to drive the running app.§8

How to use it

  1. Read the ground rules in section 2 and the decisions in section 3. They apply to every package.
  2. Find your work package in section 9. It names the requirements you own, the paths you may edit and the packages you depend on.
  3. Read the workstream section for your requirements. Open the code references before you design; line numbers were correct on 23 November 2026 and will drift.
  4. Implement inside your owned paths only. If you need a change to a shared contract that section 4 does not list, stop and ask in your report.
  5. Verify with the commands in section 10 and report in the format given there.

4Shared contracts (applied first, by the coordinator)

These are all the changes this spec needs in coordinator-owned files. They are applied once, before any package starts, so that packages can work in parallel against stable types. Every addition is optional, so the app builds and behaves as before until packages use them.

4.1 Theme

// core/types.ts — additions to interface Theme (all optional; absent = today's drawing)
  leafTextColor?: string;                 // label colour at depth >= 2; default textColor
  rootTextColor?: string;                 // label colour on a filled root; default chosen by readableInk
  rootStrokeColor?: string;               // root outline; default rootColor
  rootRadius?: number | 'pill';           // root corner radius; default min(h/2, 26)
  rootBold?: boolean;                     // default true
  mainBold?: boolean;                     // default true
  boxFillStrength?: number;               // 0..1, branch colour mixed into boxFillBase; default 0.12
  boxFillBase?: string;                   // default background
  boxStrokeWidth?: number;                // default 1.5; 0 = no outline
  boxRadius?: number | 'pill';            // default BOX_RADIUS
  nodeShadow?: ShadowSpec;                // under filled boxes at depth >= 1
  rootShadow?: ShadowSpec;
  tipTint?: number;                       // 0..1, lines at depth >= 2 mixed toward the background
  branchGradient?: boolean;               // blend along limbs leaving a main node
  fanRootJoins?: boolean;
  roundCaps?: boolean;
  tipDots?: { radius: number; gap: number };
  canvasSurface?: CanvasSurface;

export interface ShadowSpec { dy: number; blur: number; opacity: number; color?: string }   // blur = Gaussian std deviation, world units
export interface CanvasSurface {
  dots?: { color: string; opacity: number; spacing?: number };   // fixed to the world; default spacing 24
  gradient?: [string, string];                                   // top, bottom; fixed to the screen
  vignette?: number;                                             // 0..1; fixed to the screen
}

ThemeSettings (in core/model/theme-settings.ts, model-owned) adds the same keys to its Pick.

4.3 Canvas elements

export type CanvasElementKind =
  'rect' | 'ellipse' | 'diamond' | 'line' | 'arrow' | 'draw' | 'text' | 'note' | 'frame' | 'image';

export interface CanvasBinding {
  node?: NodeId;                          // a mind-map node, or
  element?: string;                       // another canvas element
  at?: Vec2;                              // fixed point on the target as 0..1 ratios; absent = nearest edge
  gap?: number;
}

export interface CanvasElement {
  id: string;
  kind: CanvasElementKind;
  x: number; y: number; w: number; h: number;   // top-left corner and size, world units (Excalidraw's x, y, width, height)
  angle?: number;                         // radians about the centre
  band?: 'back' | 'front';                // under or over the mind maps; default by kind (7.2)
  stroke?: string;                        // hex
  fill?: string;                          // hex; absent = transparent
  fillStyle?: 'solid' | 'hachure' | 'cross-hatch' | 'zigzag';
  strokeWidth?: number;                   // 1, 2 or 4
  strokeStyle?: 'solid' | 'dashed' | 'dotted';
  roughness?: 0 | 1 | 2;                  // 0 = clean geometry
  round?: boolean;
  opacity?: number;                       // 0..1
  seed: number;                           // fixes the sketch
  locked?: boolean;
  groups?: string[];                      // innermost first
  frame?: string;                         // id of the owning frame
  link?: string;
  text?: string;                          // text, note, frame name, label in a shape or on an arrow
  fontSize?: number;
  font?: 'theme' | 'hand' | 'code';
  align?: 'left' | 'center' | 'right';
  textColor?: string;
  points?: number[];                      // line, arrow, draw: x0, y0, x1, y1, … relative to (x, y)
  pressures?: number[];                   // draw: 0..1 per point
  start?: CanvasBinding;
  end?: CanvasBinding;
  startHead?: 'none' | 'arrow' | 'dot' | 'bar';
  endHead?: 'none' | 'arrow' | 'dot' | 'bar';
  elbow?: boolean;
  asset?: string;                         // image: content hash in the assets table
  source?: Record<string, unknown>;       // unused fields of an imported .excalidraw element, kept for round trip
}

export interface CanvasState {
  elements: CanvasElement[];              // array order is stacking order within a band
  bookmarks?: { id: string; name: string; view: CameraState }[];
  grid?: { size: number; snap: boolean };
}

// interface Doc
  canvas?: CanvasState;

// type Op
  | { t: 'canvas'; id: string; value?: CanvasElement; index?: number }       // insert or replace by id; no value = delete
  | { t: 'canvasMeta'; patch: Partial<Pick<CanvasState, 'bookmarks' | 'grid'>> }

5.3 Fanned centre joins: the rule

For a root box with centre (cx, cy), width w, half-height r, corner radius c, and m main branches on one side (side is 1 for right, -1 for left), numbered i = 0..m-1 from top to bottom:

step = min(0.5 * r, 1.2 * r / max(1, m - 1))
dy   = (i - (m - 1) / 2) * step            // offset of this join from the centre line
q    = max(0, |dy| - (r - c))              // how far the join sits into the rounded corner
ex   = sqrt(max(0, c*c - q*q))             // horizontal reach of the corner at that height
p0   = (cx + side * (w/2 - c + ex - 3),  cy + dy)        // start point, 3 units inside the outline

// first control point: leave roughly along the outward normal at p0
dir  = normalise(side * max(0.6, ex / max(c, 1)),  1.15 * dy / r)
c1   = p0 + dir * 1.05 * max(0.5 * levelGap, 6)

The start cap sits under the root box. The renderer draws rectangles before branches, so the root rectangle is flagged overBranches and drawn in a second rectangle call after the branch mesh. One branch on a side gives dy = 0, which is today's start point.

6.2 Model

A presentation is an ordered list of steps. A step names nodes, never camera coordinates, so it survives edits and relayout. Two sources produce steps: an automatic tour computed from the tree, and saved presentations stored in the document.

// core/types.ts (section 4.2)
export interface PresentationStep {
  id: string;
  focus: NodeId[];                       // what this step is about; the camera frames these
  reveal?: NodeId[];                     // nodes that become visible at this step, besides focus
  hide?: NodeId[];                       // nodes that stop being visible at this step
  frame?: 'nodes' | 'subtree' | 'map';   // default 'subtree': focus nodes plus what they reveal
  build?: 'all' | 'each';                // 'each': revealed nodes appear one per press
  dim?: 'others' | 'none';               // default 'others'
  title?: string;                        // default: text of the first focus node
  caption?: string;                      // one-line takeaway shown large
  note?: string;                         // speaker note; falls back to the focus node's note
  transition?: 'glide' | 'cut';
  skip?: boolean;
  seconds?: number;                      // time budget
}
export interface Presentation {
  id: string;
  name: string;
  steps: PresentationStep[];
  reveal?: 'progressive' | 'all';        // default 'progressive': the map starts folded and grows
  context?: 'dim' | 'hide';              // default 'dim'
  dimOpacity?: number;                   // default 0.22
  motion?: 'full' | 'gentle' | 'none';   // default 'full'
  targetMinutes?: number;
}
// Doc gains:  presentations?: Presentation[];
// Op gains:   { t: 'presentation'; id: string; value?: Presentation; index?: number }   // no value = delete

Visible set and opacity at a step

  • With reveal: 'all', every node that is visible in the editor is visible at every step.
  • With reveal: 'progressive', the visible set at step k is: all roots, plus every node in focus and reveal of steps 0..k, minus hide, plus all ancestors of those nodes. Jumping to any step computes the same set, so order of arrival does not matter.
  • A node folded in the document stays folded: its descendants are never visible in a presentation (decision DEC-P2).
  • Opacity: focus nodes and what this step reveals are at 1. With dim: 'others', ancestors of the focus are at 0.6 and every other visible node is at dimOpacity. With context: 'hide', the others are not drawn at all, which is today's behaviour.

Automatic tour

autoTour(doc, options) in a new core/model/presentation.ts returns steps without storing anything. Children are visited in document order, depth first.

GranularityStepsUse
branchesOne step per main branch. Focus is the branch; it reveals its whole unfolded subtree.Today's behaviour (FR-CAN-16).

Then, depth first, one step for every node that has visible children: focus is the node, it reveals its children. 7.2 Model and drawing

  • One document, one history. Canvas elements live in Doc.canvas.elements (section 4.3). Every change is a canvas op inside a transaction, so undo, the journal and crash recovery work as for nodes.
  • Two bands. Elements are drawn under the maps (back) or over them (front). Defaults: frame, rect, ellipse, diamond, note and image go to the back; arrow, line, draw and text go to the front. The user can move any element to the other band. Array order is the stacking order inside a band.
  • Geometry in core/. A new core/geometry/sketch.ts turns each element into triangles for the renderer and into SVG path data for export, from the same numbers. Sketchy outlines and hachure fills come from the rough.js generator with the element's seed, so an imported Excalidraw shape keeps its exact wobble. roughness: 0 draws clean geometry. Freehand strokes reuse the ink tessellation.
  • Text through the label atlas. Element text, note text, labels inside shapes, arrow labels and frame names are LabelDraw entries, so they stay crisp at any zoom.
  • Bindings by id. An arrow end bound to a node or element stores the target's id. The end point is computed when the scene is built, from the target's current box, so arrows follow when a map relayouts.
  • Font. font: 'theme' uses the map theme's family; 'hand' uses "Chalkboard SE", "Marker Felt", "Comic Sans MS", cursive; 'code' uses a monospace stack. No font is bundled.

8Agent tooling

Today an agent can read any saved map and send three kinds of edit (add, rename, set a note) to one map that is open in the app, under a 15-minute grant. It cannot create a map, style it, move or delete anything, change layout or theme, render a picture, or see the result.

This workstream grows tools/agent-cli.ts into one radiant command that an agent can use to draw any map: write a whole map as a text spec, change an existing one with small operations, check the result as numbers and as a picture, and drive the running app. The research, worked examples and options are in Radiant-Agent-Tooling-Requirements_2026-11-23.html; this section fixes the decisions and carries the requirements.
